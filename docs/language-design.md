# Spell 言語設計メモ

2026-11-21 の設計議論の記録。実装仕様ではなく、決定事項と未決定事項の整理である。
元の設計の正本は spell_v0 の `DESIGN.md`、`docs/reference.html`、`docs/design-review.md` とし、
本メモは主にそれとの差分と、新しい spell での新規決定を記録する。

なお、この `docs/` は将来 GitHub Pages でドキュメントを公開する土台にする想定である。

## 目標

- 競技プログラミングで便利で、速く書けて、デバッグしやすい言語にする
- 優先順位は spell_v0 を踏襲する: 実行速度 > 打鍵数の少なさ > 競プロ頻出処理の支援 > 楽しさ > 一貫性 > 読みやすさ > 汎用性
- ただし読みやすさは「初見で理解できるか」ではなく「慣れた利用者が速く正確に読めるか」で測る

## 基本原則

1. **コアは小さく地味に保ち、spell らしさは糖衣構文で作る**
   - コアは変数・関数・分岐・ループ・配列・基本入出力だけの平凡な言語にする
   - spell らしい短縮や記号は、すべてコアへ展開できる糖衣として置く
2. **記号糖衣の採否は、初見の読みやすさでは決めない**
   - 判定条件は「頻出であること」「1記号1意味で、一意に展開できること」「糖衣の語彙総量を小さく保てること」
   - 頻度が低い記号は慣れが効かないため、原則として採用しない
3. **記号糖衣は、必ずアルファベット形の正規表記を持つ**
   - 展開コマンドは、記号形からアルファベット形への書き直しまでを行う（コアへの完全展開はしない）
   - 展開結果も、そのまま実行できる spell でなければならない（デバッグ時の切り分けに使うため）
4. **糖衣の採用基準は spell_v0 の design-review を継承する**
   - 代表問題で繰り返し現れる
   - コア操作への展開が明確で、実行時コストを増やさない
   - 既存の短縮構文と記号の役割が衝突しない
   - 型エラーと生成コードを利用者が追跡できる

## 決定: for と範囲

- `for` の3形態は spell_v0 を継承する
  1. 整数レンジ（`for i in n:` は 0 から n-1）
  2. 配列・文字列の要素走査（走査変数は要素への可変参照）
  3. 回数リピート（`for n:`、束縛変数なし）
- **短縮形は `@` を spell_v0 のまま採用する**: `i@n:`、`i@0..n:`、`@n:`（変数なしリピート）、`ai@a:`（要素走査）。正規形は `for` を使った形で、展開コマンドでそちらへ書き直せる
  - 併せて、break の省略形 `!` と continue の省略形 `^` も spell_v0 のまま採用する
  - 検討して却下した代替案: `i~n:`（`i..n` と見間違える）、`for` を落とす形（分かりにくい）、`i::n:`、`i$n:`、`for i..n:` の融合形。最終的に `@` へ戻した
- 右辺の式は最初に1回だけ評価する。本体で式に使われた変数を書き換えても反復回数は変わらない
- 回数が0や負数のときは0回で、何もしない
- ループ変数はフラットスコープの普通の変数として残る。終了後の値は範囲の外側の値とする
- 範囲は spell_v0 を継承する: `a..b` は半開区間 [a, b)、`a..=b` は終端を含む [a, b]
- **`.rev` を基本操作として新設する**（spell_v0 には存在しない）。範囲・配列・文字列の並びを逆順にする
- **逆範囲は糖衣とする**
  - `a..b`（a > b のとき）は `(b..a).rev` の省略形
  - `a..=b`（a > b のとき）は `(b..=a).rev` の省略形
  - 端点の扱いは「集合は昇順と同じで、順序だけが逆」。例: `n..0` は n-1, n-2, ..., 0
  - 変数が端点で実行時に大小が決まる場合も、意味は「始点の側から終点へ向かう並び」で一貫させる
  - 展開コマンドでの正規形は `(0..n).rev` の形である
- ライブラリ関数の契約は spell_v0 を継承する。`bisect` は昇順範囲を受ける。`a.sum(l..r)` は 0 <= l <= r を前提とする

## 決定: 入出力

spell_v0 で確定済みのものは継承する。

- 入力: `x = in`、`s = in_str`、`a, b = in`、`a = in[n]`、`a- = in[n]`、`words = in_str[n]`、既存要素への `>> a[i]`。`in` は代入の右辺全体でのみ使用できる
- 短縮形: 入力 `>> x`、出力 `<< x`
- 出力: `put` は配列を空白区切りで1行に、二次元配列は行ごとに改行して出す。Bool は 1 / 0
- `yn` による Yes / No 出力、`cerr` による stderr へのデバッグ出力（提出モードで自動除去）

新規の決定:

- **行入力を追加する**: `s = in_line` を `in_str` と並ぶ形で置き、空白を含む行を読めるようにする（spell_v0 はトークン読みのみで、design-review でも弱点とされていた）
- **二次元入力は `a = in[h][w]` と書く**: `in[w]` を h 回読む合成として定義し、結果は二次元配列（Array<Array<Int>>）になる。`a[y][x]` でアクセスでき、`put` の二次元配列の行ごと出力や `for row in a` とそのまま噛み合う。辺リストは `a = in[n][2]` と書く
  - 一次元で読みたい場合は、従来通り `a = in[h * w]` も書ける（個数が任意の式でよい、という `in[n]` の一般性はそのまま残る）
  - 文字グリッドは従来通り `in_str[h]` で行ごとの文字列として読む
- **入力の過不足は、手元の実行では静かに通さない**: 読みすぎたら即エラーにする。終了時に読み残しがあったら警告する（読み個数のずれを早期に見つけるため。提出モードでの扱いはデバッグ設計と一緒に決める）
- **`put x, y` の複数値出力を正式に認める**: 空白区切りで並べて、末尾に改行を付ける

## 決定: デバッグ設計

spell_v0 の現状は、`--submit` で `cerr` を除去できるだけで、境界チェックなどの切り替えは未実装だった（DESIGN.md の構想のみ）。新しい spell では次で確定する。

- **モードの原則**: 同じソースから Debug（手元の実行）と Submit（提出用）の2つのビルドを作る。検査は正しいプログラムの意味を変えず、壊れた状態を静かに通すか、その場で止めるかだけを変える
- **エラー表示**: spell の言葉で、発生した行と関係した値を含めて出す（例: 添字の値と配列の長さ）
- **Debug で検査するもの**:
  - 配列の境界外アクセス（読み書き両方）。安全添字 `a?[i]` は「範囲外かもしれない」の意思表示として対象外にし、spell_v0 の意味（条件式・比較式では false）を変えない
  - 整数オーバーフロー、0除算
  - 入力の読みすぎ（即エラー）と読み残し（警告）
  - 空配列への `a.min` / `a.max` のようなライブラリの契約違反
- **Submit での扱い**: 境界外アクセスは未定義（速度優先）。ただし整数オーバーフローは「2の補数で巻き戻る」と定義し、挙動の決定性は残す
- **`cerr`**: spell_v0 を継承し、提出モードで除去される。引数が変数や添字式のときは `x = 3` のように名前つきで出す
- **`assert`**: 置く。Debug では失敗した行と式を出して止まる。**Submit では除去する**。そのため、assert の条件式に副作用を書くとモード間で挙動が変わるので、条件は副作用なしを規約とする

## 決定: エラー出力

- エラーは4分類し、出し方を分ける: (1) 字句・構文エラー（コンパイル時、位置つき） (2) 意味エラー（コンパイル時、位置つき。未定義変数の読み取りなど） (3) 実行時エラー（Debug 検査が止めるもの。位置＋関係した値つき） (4) 内部エラー（コンパイラのバグ。「プログラムではなくコンパイラ側の問題」と明示し、内部情報を出してよいのはこの分類だけ）
- 文面は日本語で、spell の言葉で書く（レジスタ名や実装言語の都合は出さない）。「期待したもの」と「実際のもの」を両方出す
- 最初のエラーで即終了する（エラー回収はしない）。警告（読み残した入力など）は同じ形式で、終了しない
- 表示形式: 先頭に `ファイル名:行:列: エラー: 文面`、続けて行番号つきでその行を表示し、問題のトークンの範囲いっぱいに `^` の下線を引く（1点のキャレットではない）
- 実行時エラーも同じフル表示にする。そのため Debug ビルドでは、検査のある行の本文をバイナリへ埋め込む（埋め込みは Debug のみ、対象は検査のある行だけ）
- 未定義変数のエラーでは typo の候補提示を行う: 編集距離の近い既存変数があれば「もしかして `名前` ですか（定義は N 行目）」と添える。対象は未定義変数のエラーに限る
- 細部: 色付けは標準エラーが端末のときだけ（パイプ時はプレーン）。下線の範囲が複数行に及ぶ場合は、表示している行の範囲内だけを引く

### エラー出力の追加決定（Sol レビューを経て）

- 分類に **ドライバエラー** を加える（計5分類）: ソースファイルが開けない、外部アセンブラ／リンカの起動失敗など、ソース位置を持たない失敗。内部エラーとは分ける。実行時エラーのフル表示が約束できるのは spell の検査が検出した失敗だけで、OS に強制終了された場合まで約束しない
- 指す対象は「トークン全体」固定ではなく **主位置**（原因を説明する範囲、または挿入点）とする: `)` の欠落のような場合はゼロ幅の挿入点に `^` を1つ置く。実行時エラーでは式全体ではなく原因の部分（`a[i]` なら `i`、`x / y` なら `y`）を指す
- 関連する別の場所は2件目のエラーにせず **補足位置** として示す（対応する開き括弧の位置、定義位置など）。文面でも事実は `補足:`、推測は `ヒント:` と書き出しを分ける（typo 候補は `ヒント:`）
- 位置の内部表現はバイト範囲 `[start, end)`、行・列は1始まり。列番号は Unicode コードポイント単位で数え、下線は表示幅で合わせる。タブは表示時に展開する（日本語コメント等の全角文字で下線がずれないようにするため）
- 位置がないエラーでは見出しの位置を省く（`0:0` のような架空の位置は出さない）
- 入力エラーは理由を分ける（入力の終わりに達した／形式が違う／値が範囲外）。読み残し警告は、既に読み込んだバッファ内に非空白の残りがある場合だけ出す（追加の読み取りで端末やパイプを待ち続けないため。警告がないことは読み残しなしの保証にはならない）
- typo 候補の出し方: エラー地点から参照できる変数だけを対象にし、短い名前ほど厳しく判定する。同率・僅差なら出さない。最大1件
- Debug 検査は危険な演算より前に行い、オペランドを二重評価しない（符号付き最小値を -1 で割る場合もゼロ除算と並ぶ検査対象）
- `assert` と `cerr` は Submit で引数ごと評価しない、を仕様として明記する（既存の「副作用を持たせない」注意の格上げ）。除去されるコードも両モードで意味検査は行う

## 決定: フルクラスとダンダーメソッド規約

- **フルクラスを新設する**（spell_v0 にはクラスもユーザー定義型もなかった）。自作データ構造（セグメント木、Union-Find など）を spell のライブラリとして書けることが、競プロ用途での大きな利点になる
- 動機のもう半分は、コンパイラからライブラリ都合の特殊扱いを消すこと。現在の `.len` は、パーサが特別扱いし、コード生成が「要素の手前に長さを置く」という配列の表現を直接知っている。これをやめる
- 演算子・添字・長さ・反復は **ダンダーメソッド規約への展開** とする: `a[i]` → `__getitem__`、`a[i] = x` → `__setitem__`、長さ → `__len__`、`for x in a` → 反復の規約、など。コンパイラが持つのはフィールドアクセスとメソッド呼び出しの一般機構と、この展開規則だけ
- 配列や文字列も prelude でクラスとして定義する。コンパイラに残る原始機能は、連続領域の確保など最小限に痩せさせる
- **継承はなし**: ダンダー規約は「その名前のメソッドがあるか」だけで成立するので継承は不要。共有は委譲で足りる。型推論とメソッド解決を軽く保つ
- **`self` は Python 式に明示する**: メソッドの最初の引数として書き、中では `self.data` と書く。裸の名前はローカル変数、`self.` つきはフィールド、と区別を固定する（代入で変数が生まれる言語なので、この区別が曖昧だと事故になる）
- **クラスまわりの構文は可読性優先**: クラスはコンテスト中に書くものではなく、事前にライブラリとして書いておくものなので、打鍵数より可読性を優先する（コンテスト中のコードに適用する速さの基準とは使い分ける）
- **フィールドはクラス本体で宣言する**: フィールドの一覧が一目で分かり、レイアウトが宣言で固定される（静的型＋推論との相性もよい）。`__init__` の代入で生やす Python 式は採らない
- **ダンダーとコンストラクタは Python 式の `__名前__` で統一する**: コンストラクタは `__init__(self, ...)`、長さは `__len__`、添字は `__getitem__` / `__setitem__` など。アンダースコア2つが「規約専用の別枠」の目印になり、通常のメソッド名と衝突しない
- 未決定の詳細: クラスの構文の字面、型注釈の字面と書ける場所の範囲

## 決定: 型注釈は任意（クラスでは明示が推奨スタイル）

- **型注釈は書いても書かなくてもよい**とする。spell_v0 の「型注釈を一切なくし、すべて推論する」方針からの変更。書いた注釈は推論結果と照合される制約になり、書かなければ推論される
- **クラス（=事前に書くライブラリ）では型を明示して書くのを推奨スタイルとする**: フィールドとメソッドのシグネチャに型を付け、契約を固定する。可読性優先の原則の適用で、v0 の「シグネチャは最初の呼び出し箇所から遅延推論する」方式の不安定さ（ライブラリ側の契約が利用側で決まってしまう）への対策にもなる
- コンテスト中に書くコードでは省略して速さを取る。型パラメータもこの枠組みで扱う（クラス定義側で明示し、利用側では推論）
- 未決定: 型注釈の字面（コロン式など）、注釈を書ける場所の範囲（変数・フィールド・引数・戻り値）

## 速く書ける構文の候補（頻度順）

ほぼ全ての問題で使う層:

- 入力: `n = in`、`a, b = in`、`a = in[n]`、`a- = in[n]`（入力修飾子 `-` の正規形は `-= 1` への展開）
- 出力: `put x`、`put x, y`、`put a`（配列を空白区切りで出す形は採用方向）
- ループ: 上記の `for`
- 更新: 複合代入、`ans++`（正規形は `ans += 1`）、`a, b = b, a` の交換

頻出層:

- `x <?= y` / `x >?= y`（正規形は `chmin` / `chmax`）
- 連鎖比較 `a < b > c`（正規形は `and` で繋いだ形）
- 配列メソッド: `a.sum`、`a.len`、`a.min`、`a.max`、`a.sort`、`a.rev`、区間和、二分探索
- スライスと範囲: `a[1..]` など

## 未決定事項

- 数え上げ用の辞書で、未登録キーを黙って0で生やすか（`cnt[x]++`）。速さと引き換えに、キーの綴り間違いを検出できなくなる。数え上げ専用の型でのみ許可する案がある
- `<?=` のアルファベット形を関数風（`chmin(x, y)`）にするか、文として扱うか。値を返しつつ代入先を書き換える性質の扱い
- spell_v0 の `for ... else` の最終確認（継承前提で置いている）
- 除算・剰余の負数セマンティクス（C 方式の切り捨てか、Python 方式の床か）。現在の実装は C 方式
- spell 化フェーズの実装言語（C で続けるか、Rust で書き直すか）。糖衣・型推論・展開コマンドの実装に入る前に決める
- 保留（後回しでよい）: Float の詳細設計、sort のカスタム比較、三項演算子、累乗の記号、グリッド走査の糖衣

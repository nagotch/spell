# Spell 言語設計メモ

2026-11-21 の設計議論の記録。実装仕様ではなく、決定事項と未決定事項の整理である。
元の設計の正本は spell_v0 の `DESIGN.md`、`docs/reference.html`、`docs/design-review.md` とし、
本メモは主にそれとの差分と、新しい spell での新規決定を記録する。

なお、この `docs/` は将来 GitHub Pages でドキュメントを公開する土台にする想定である。

## 目標

- 競技プログラミングで便利で、速く書けて、デバッグしやすい言語にする
- 優先順位は spell_v0 を踏襲する: 実行速度 > 打鍵数の少なさ > 競プロ頻出処理の支援 > 楽しさ > 一貫性 > 読みやすさ > 汎用性
- ただし読みやすさは「初見で理解できるか」ではなく「慣れた利用者が速く正確に読めるか」で測る

## 基本原則

1. **コアは小さく地味に保ち、spell らしさは糖衣構文で作る**
   - コアは変数・関数・分岐・ループ・配列・基本入出力だけの平凡な言語にする
   - spell らしい短縮や記号は、すべてコアへ展開できる糖衣として置く
2. **記号糖衣の採否は、初見の読みやすさでは決めない**
   - 判定条件は「頻出であること」「1記号1意味で、一意に展開できること」「糖衣の語彙総量を小さく保てること」
   - 頻度が低い記号は慣れが効かないため、原則として採用しない
3. **記号糖衣は、必ずアルファベット形の正規表記を持つ**
   - 展開コマンドは、記号形からアルファベット形への書き直しまでを行う（コアへの完全展開はしない）
   - 展開結果も、そのまま実行できる spell でなければならない（デバッグ時の切り分けに使うため）
4. **糖衣の採用基準は spell_v0 の design-review を継承する**
   - 代表問題で繰り返し現れる
   - コア操作への展開が明確で、実行時コストを増やさない
   - 既存の短縮構文と記号の役割が衝突しない
   - 型エラーと生成コードを利用者が追跡できる
5. **コンパイラは最小限にし、ライブラリ側で充実させる**
   - コンパイラが知るのは汎用の仕組み（変数・関数・クラスとメソッド呼び出し・ダンダーへの展開規則・最小限の intrinsic）だけにする
   - 配列や文字列のような具体的な型の振る舞いも、コンパイラの特殊扱いではなく prelude のクラス定義として置く
   - 機能を足したくなったら、まずライブラリで書けないかを考え、書けない場合だけコンパイラ側の最小の原始機能を足す
6. **基本は Pythonic にする**
   - 意味論や基本構文で判断に迷う点は、Python の意味論を既定とする（反復、トップレベル、除算・剰余など、個別の決定もこの原則に沿う）
   - ただし既決の事項（打鍵数優先の糖衣、優先順位づけ）はこの原則より優先する。Python に寄せるのは未決定の迷いどころだけ

## 決定: for と範囲

- `for` の3形態は spell_v0 を継承する
  1. 整数レンジ（`for i in n:` は 0 から n-1）
  2. 配列・文字列の要素走査（走査変数は要素への可変参照）
  3. 回数リピート（`for n:`、束縛変数なし）
- **短縮形は `@` を spell_v0 のまま採用する**: `i@n:`、`i@0..n:`、`@n:`（変数なしリピート）、`ai@a:`（要素走査）。正規形は `for` を使った形で、展開コマンドでそちらへ書き直せる
  - 併せて、break の省略形 `!` と continue の省略形 `^` も spell_v0 のまま採用する
  - 検討して却下した代替案: `i~n:`（`i..n` と見間違える）、`for` を落とす形（分かりにくい）、`i::n:`、`i$n:`、`for i..n:` の融合形。最終的に `@` へ戻した
- 右辺の式は最初に1回だけ評価する。本体で式に使われた変数を書き換えても反復回数は変わらない
- 回数が0や負数のときは0回で、何もしない
- ループ変数はフラットスコープの普通の変数として残る。終了後の値は範囲の外側の値とする
- 範囲は spell_v0 を継承する: `a..b` は半開区間 [a, b)、`a..=b` は終端を含む [a, b]
- **`.rev` を基本操作として新設する**（spell_v0 には存在しない）。範囲・配列・文字列の並びを逆順にする
- **逆範囲は糖衣とする**
  - `a..b`（a > b のとき）は `(b..a).rev` の省略形
  - `a..=b`（a > b のとき）は `(b..=a).rev` の省略形
  - 端点の扱いは「集合は昇順と同じで、順序だけが逆」。例: `n..0` は n-1, n-2, ..., 0
  - 変数が端点で実行時に大小が決まる場合も、意味は「始点の側から終点へ向かう並び」で一貫させる
  - 展開コマンドでの正規形は `(0..n).rev` の形である
- ライブラリ関数の契約は spell_v0 を継承する。`bisect` は昇順範囲を受ける。`a.sum(l..r)` は 0 <= l <= r を前提とする

## 決定: 入出力

spell_v0 で確定済みのものは継承する。

- 入力: `x = in`、`s = in_str`、`a, b = in`、`a = in[n]`、`a- = in[n]`、`words = in_str[n]`、既存要素への `>> a[i]`。`in` は代入の右辺全体でのみ使用できる
- 短縮形: 入力 `>> x`、出力 `<< x`
- **`>> a, b, c` の複数対象（step 62）**: 対象をカンマで並べると、各対象へ `in` を左から順に代入する並び（`a = in; b = in;`）へ展開する。対象の形は単独形と同じ（識別子・添字・メンバー）。`in[n]` などの他形式は対象ごとに書けない
- 出力: `put` は配列を空白区切りで1行に、二次元配列は行ごとに改行して出す。Bool は 1 / 0
- `yn` による Yes / No 出力、stderr への出力は `eprint`（step 59 で `cerr` を統合。後述）

新規の決定:

- **行入力を追加する**: `s = in_line` を `in_str` と並ぶ形で置き、空白を含む行を読めるようにする（spell_v0 はトークン読みのみで、design-review でも弱点とされていた）
- **二次元入力は `a = in[h][w]` と書く**: `in[w]` を h 回読む合成として定義し、結果は二次元配列（Array<Array<Int>>）になる。`a[y][x]` でアクセスでき、`put` の二次元配列の行ごと出力や `for row in a` とそのまま噛み合う。辺リストは `a = in[n][2]` と書く
  - 一次元で読みたい場合は、従来通り `a = in[h * w]` も書ける（個数が任意の式でよい、という `in[n]` の一般性はそのまま残る）
  - 文字グリッドは従来通り `in_str[h]` で行ごとの文字列として読む
- **入力の過不足は、手元の実行では静かに通さない**: 読みすぎたら即エラーにする。終了時に読み残しがあったら警告する（読み個数のずれを早期に見つけるため。提出モードでの扱いはデバッグ設計と一緒に決める）
- **`put x, y` の複数値出力を正式に認める**: 空白区切りで並べて、末尾に改行を付ける

## 決定: デバッグ設計

spell_v0 の現状は、`--submit` で `cerr` を除去できるだけで、境界チェックなどの切り替えは未実装だった（DESIGN.md の構想のみ）。新しい spell では次で確定する。

- **モードの原則**: 同じソースから Debug（手元の実行）と Submit（提出用）の2つのビルドを作る。検査は正しいプログラムの意味を変えず、壊れた状態を静かに通すか、その場で止めるかだけを変える
- **エラー表示**: spell の言葉で、発生した行と関係した値を含めて出す（例: 添字の値と配列の長さ）
- **Debug で検査するもの**:
  - 配列の境界外アクセス（読み書き両方）。安全添字 `a?[i]` は「範囲外かもしれない」の意思表示として対象外にし、spell_v0 の意味（条件式・比較式では false）を変えない
  - 整数オーバーフロー、0除算
  - 入力の読みすぎ（即エラー）と読み残し（警告）
  - 空配列への `a.min` / `a.max` のようなライブラリの契約違反
- **Submit での扱い**: 境界外アクセスは未定義（速度優先）。ただし整数オーバーフローは「2の補数で巻き戻る」と定義し、挙動の決定性は残す
- **`cerr`**: spell_v0 を継承し、提出モードで除去される。引数が変数や添字式のときは `x = 3` のように名前つきで出す（step 59 で、stderr への出力そのものは `eprint` として先行実装した。独立した `cerr` 構文は入れず、提出モードで除去する対象は将来 `eprint` とする）
- **`assert`**: 置く。Debug では失敗した行と式を出して止まる。**Submit では除去する**。そのため、assert の条件式に副作用を書くとモード間で挙動が変わるので、条件は副作用なしを規約とする

## 決定: エラー出力

- エラーは4分類し、出し方を分ける: (1) 字句・構文エラー（コンパイル時、位置つき） (2) 意味エラー（コンパイル時、位置つき。未定義変数の読み取りなど） (3) 実行時エラー（Debug 検査が止めるもの。位置＋関係した値つき） (4) 内部エラー（コンパイラのバグ。「プログラムではなくコンパイラ側の問題」と明示し、内部情報を出してよいのはこの分類だけ）
- 文面は日本語で、spell の言葉で書く（レジスタ名や実装言語の都合は出さない）。「期待したもの」と「実際のもの」を両方出す
- 最初のエラーで即終了する（エラー回収はしない）。警告（読み残した入力など）は同じ形式で、終了しない
- 表示形式: 先頭に `ファイル名:行:列: エラー: 文面`、続けて行番号つきでその行を表示し、問題のトークンの範囲いっぱいに `^` の下線を引く（1点のキャレットではない）
- 実行時エラーも同じフル表示にする。そのため Debug ビルドでは、検査のある行の本文をバイナリへ埋め込む（埋め込みは Debug のみ、対象は検査のある行だけ）
- 未定義変数のエラーでは typo の候補提示を行う: 編集距離の近い既存変数があれば「もしかして `名前` ですか（定義は N 行目）」と添える。対象は未定義変数のエラーに限る
- 細部: 色付けは標準エラーが端末のときだけ（パイプ時はプレーン）。下線の範囲が複数行に及ぶ場合は、表示している行の範囲内だけを引く

### エラー出力の追加決定（Sol レビューを経て）

- 分類に **ドライバエラー** を加える（計5分類）: ソースファイルが開けない、外部アセンブラ／リンカの起動失敗など、ソース位置を持たない失敗。内部エラーとは分ける。実行時エラーのフル表示が約束できるのは spell の検査が検出した失敗だけで、OS に強制終了された場合まで約束しない
- 指す対象は「トークン全体」固定ではなく **主位置**（原因を説明する範囲、または挿入点）とする: `)` の欠落のような場合はゼロ幅の挿入点に `^` を1つ置く。実行時エラーでは式全体ではなく原因の部分（`a[i]` なら `i`、`x / y` なら `y`）を指す
- 関連する別の場所は2件目のエラーにせず **補足位置** として示す（対応する開き括弧の位置、定義位置など）。文面でも事実は `補足:`、推測は `ヒント:` と書き出しを分ける（typo 候補は `ヒント:`）
- 位置の内部表現はバイト範囲 `[start, end)`、行・列は1始まり。列番号は Unicode コードポイント単位で数え、下線は表示幅で合わせる。タブは表示時に展開する（日本語コメント等の全角文字で下線がずれないようにするため）
- 位置がないエラーでは見出しの位置を省く（`0:0` のような架空の位置は出さない）
- 入力エラーは理由を分ける（入力の終わりに達した／形式が違う／値が範囲外）。読み残し警告は、既に読み込んだバッファ内に非空白の残りがある場合だけ出す（追加の読み取りで端末やパイプを待ち続けないため。警告がないことは読み残しなしの保証にはならない）
- typo 候補の出し方: エラー地点から参照できる変数だけを対象にし、短い名前ほど厳しく判定する。同率・僅差なら出さない。最大1件
- Debug 検査は危険な演算より前に行い、オペランドを二重評価しない（符号付き最小値を -1 で割る場合もゼロ除算と並ぶ検査対象）
- `assert` と `cerr` は Submit で引数ごと評価しない、を仕様として明記する（既存の「副作用を持たせない」注意の格上げ）。除去されるコードも両モードで意味検査は行う

## 決定: フルクラスとダンダーメソッド規約

- **フルクラスを新設する**（spell_v0 にはクラスもユーザー定義型もなかった）。自作データ構造（セグメント木、Union-Find など）を spell のライブラリとして書けることが、競プロ用途での大きな利点になる
- 動機のもう半分は、コンパイラからライブラリ都合の特殊扱いを消すこと。現在の `.len` は、パーサが特別扱いし、コード生成が「要素の手前に長さを置く」という配列の表現を直接知っている。これをやめる
- 演算子・添字・長さ・反復は **ダンダーメソッド規約への展開** とする: `a[i]` → `__getitem__`、`a[i] = x` → `__setitem__`、長さ → `__len__`、`for x in a` → 反復の規約、など。コンパイラが持つのはフィールドアクセスとメソッド呼び出しの一般機構と、この展開規則だけ
- 配列や文字列も prelude でクラスとして定義する。コンパイラに残る原始機能は、連続領域の確保など最小限に痩せさせる
- **継承はなし**: ダンダー規約は「その名前のメソッドがあるか」だけで成立するので継承は不要。共有は委譲で足りる。型推論とメソッド解決を軽く保つ
- **`self` は Python 式に明示する**: メソッドの最初の引数として書き、中では `self.data` と書く。裸の名前はローカル変数、`self.` つきはフィールド、と区別を固定する（代入で変数が生まれる言語なので、この区別が曖昧だと事故になる）
- **クラスまわりの構文は可読性優先**: クラスはコンテスト中に書くものではなく、事前にライブラリとして書いておくものなので、打鍵数より可読性を優先する（コンテスト中のコードに適用する速さの基準とは使い分ける）
- **フィールドはクラス本体で宣言する**: フィールドの一覧が一目で分かり、レイアウトが宣言で固定される（静的型＋推論との相性もよい）。`__init__` の代入で生やす Python 式は採らない
- **ダンダーとコンストラクタは Python 式の `__名前__` で統一する**: コンストラクタは `__init__(self, ...)`、長さは `__len__`、添字は `__getitem__` / `__setitem__` など。アンダースコア2つが「規約専用の別枠」の目印になり、通常のメソッド名と衝突しない
- クラス構文の字面: `class SegTree:` / 型パラメータつきは `class SegTree<T>:`。メソッドはクラス内でも `def` を使い、`self` に注釈は付けない（所属クラスから決まる）
- フィールド宣言は `data: Array<T>` の形で、**型が必須**（これは任意注釈ではなくフィールドそのものの宣言）。`self.x = ...` は宣言済みフィールドへの代入に限り、未宣言名への代入はエラー
- フィールドの初期値はクラス本体に書かず、`__init__` での代入に集約する。コンパイラは「正常終了する全経路で全フィールドが初期化されること」と「初期化前の読み取りがないこと」を検査する
- 型パラメータは定義側で明示し、生成時は `SegTree(...)` と書いて、コンストラクタ引数と束縛先の注釈の両方から推論する。どちらからも決まらなければ、注釈を求めるエラーにする。`<...>` は初版では型を書く位置にだけ置く
- コンパイラ組み込み（intrinsic）は v0 と同じ `__spell_` 接頭辞の名前で、prelude のクラスメソッドの本体に閉じ込める
- **0引数メソッドは `()` を省略できる**（ドットの後に限る）: `a.len` は、フィールドなら読み出し、`self` 以外の引数を持たないメソッドならその呼び出しとして解決する。同名のフィールドとメソッドの共存は禁止し、静的に一意に決める
- これにより **`len` は Array 等の普通のメソッドとし、`__len__` は設けない**。ダンダーは構文が起点になる操作（添字・演算子・反復など）に限る。既定の `.rev` もこの規則で説明できる
- メソッドを関数値として欲しい場合はラムダで包む（`a.m` の意味が期待型で変わる規則は採らない）。メソッドを値として渡す書き方はそもそも可読性が下がり、コンテスト中にはやらないので、ラムダで十分という判断。トップレベルの関数には省略を広げない（`f` は関数値、`f()` が呼び出し）
- メソッドへの代入（`a.len = 3` 等）はエラーとする（暗黙の setter は作らない）。関数型フィールドの `a.m()` は、フィールドの関数値を呼び出すものとして区別される
- ライブラリのスタイル: 括弧なしで書けるメソッドは、計算量と破壊的かどうかを API 側で明記する（フィールド読み出しに見えるため）

## 決定: 型注釈は任意（クラスでは明示が推奨スタイル）

- **型注釈は書いても書かなくてもよい**とする。spell_v0 の「型注釈を一切なくし、すべて推論する」方針からの変更。書いた注釈は推論結果と照合される制約になり、書かなければ推論される
- **クラス（=事前に書くライブラリ）では型を明示して書くのを推奨スタイルとする**: フィールドとメソッドのシグネチャに型を付け、契約を固定する。可読性優先の原則の適用で、v0 の「シグネチャは最初の呼び出し箇所から遅延推論する」方式の不安定さ（ライブラリ側の契約が利用側で決まってしまう）への対策にもなる
- コンテスト中に書くコードでは省略して速さを取る。型パラメータもこの枠組みで扱う（クラス定義側で明示し、利用側では推論）
- 型注釈の字面は v0 の prelude と同じ: 引数・束縛は `名前: 型`、戻り値は `-> 型`、型引数は `Array<Int>` の形
- 注釈を書ける場所: フィールド（必須、上記）、引数（任意）、戻り値（任意）、ローカル変数の初回束縛 `x: Int = 式`（任意）。再代入への注釈と、初期値なしのローカル宣言は初版では入れない
- 注釈はキャストではなく型制約で、推論の事後照合だけでなく、注釈側から右辺・生成式の推論へも制約を渡す（双方向）

## 決定: 実装言語は C で継続する（Rust 移行は取りやめ）

- 2026-11-23 午前、一度は spell 化フェーズの実装言語を Rust とする決定をしたが、同日、再判断で取りやめた。理由: 既に C で実装が進んでいる以上、移植コストのほうが利得より大きい
- C 版が本線のまま続く。残課題は本のステップ（コメント、グローバル変数）、`%`、`&&` / `||` / `!`、その先の spell 化フェーズ（字下げ構文・型推論など）
- 本書の言語設計の決定（最小コア＋prelude、脱糖フェーズ、クラスとダンダー、エラー出力など）は実装言語に依存しない設計として有効なまま。脱糖規則の実装は C の構文木書き換えとして行う（仕様は項書き換えの記法で記述し、実装と対応させる方針は変わらない）

## 決定: 除算と剰余

- **除算は床除算、剰余は除数と同じ符号（Python 式）**: `-7 / 2` は `-4`、`-7 % 2` は `1`。`a == (a / b) * b + a % b` が常に成り立ち、正の除数では剰余は常に非負になる
- 現在の C 実装はハードウェアの切り捨てのままで、この決定に合わせて補正する作業が残る

## 決定: トップレベルとグローバル変数

- **トップレベルには文・関数定義・クラス定義を混ぜて書ける**（v0 / Python 式）。文は上から順に実行され、`main` 関数の入れ物は不要
- トップレベルでの代入がグローバル変数の作成になり、関数の中から読み書きできる。これがグローバル変数の表面構文を兼ねる

## 決定: 脱糖フェーズと for の while 化

- **コンパイラ前段に脱糖（lowering）フェーズを設ける**: 構文解析後の構文木を歩き、糖衣のノードをコアのノードの組み合わせに置き換える。`for` 単独ではなく、複数の構文を共通基盤でまとめて下ろすことで意味を持つ
- 脱糖で下ろす対象: `for`（範囲・要素・回数）→ `while` と反復プロトコル、`for...else` → 終了フラグつき `while`、`elif` → 入れ子の `if`、`!` / `^` → `break` / `continue`、複数代入・分割代入 → 一時変数への退避＋個別代入、比較の連鎖 → 一時変数＋短絡、複合代入・増減・`<?=` → 読み出し・演算・書き戻し（左辺の評価は1回だけ）、`a..b` → Range の生成、`.rev` と0引数メソッドの括弧省略 → 通常のメソッド呼び出し、添字・演算子 → ダンダー呼び出し、入出力構文 → ライブラリ呼び出し
- 下ろした後に残る最小コア: リテラル、変数、関数・メソッド呼び出し、基本演算、単一代入、ブロック、`if`、`while`、`break`、`continue`、`return`、関数定義、クラスの実行時モデル
- 共有基盤: 隠しシンボルの発行（ソースから参照できない内部シンボル。フラットスコープに漏らさない）、生成ノードへの元のソース位置のコピー、評価順序を守るため一時変数化、ループ文脈の管理（どの `break` / `continue` がどのループ宛か）
- `for` の展開の要所: 範囲の端点は1回だけ評価して隠し変数へ。その `for` 宛の `continue` はステップ処理（カウンタ加算）を通る形に書き換える
- **ループ変数は内部カウンタとは別（Python 式）**: 本文でループ変数を書き換えても反復には影響しない。ループ後のループ変数は最後に反復した値を保持し、範囲が空なら代入自体が起きない（従前の状態のまま）。旧決定「範囲外の値で終わる」はこの決定で置き換える
- **`for ... else` は継承する**: break しなかったときだけ else 側を実行する（Python と同じ）。脱糖では終了フラグで実現する
- **要素反復はイテレータプロトコルに統一（Python 式）**: `for x in obj` は `obj.__iter__()` の返すイテレータから値を取り出す形に展開する。配列・範囲もイテレータを返す。範囲反復の内部カウンタもイテレータ側が持つため、「ループ変数を書き換えても反復に影響しない」とも一貫する
- **ループ変数への代入は要素へ書き戻す（step 58、旧決定「代入しても書き戻らない」を変更）**: イテレータが任意メソッド `__set_current__(v)` を持つ場合、本体でのループ変数への代入は各反復の終わり（と、このループ宛の `break` / `continue` の直前）に書き戻される。配列（`ArrayIter`）と文字列（`StrIter`）が持つ。持たない反復（範囲・Dict のキーなど）でのループ変数への代入は、書き戻されずに消える事故を防ぐためコンパイルエラーにする。`return` で抜ける場合は書き戻さない。あわせて、文字列の反復は1文字ずつの `str` を返すよう変更（添字 `s[i]` は従来どおり `int` の文字コードを返す）
- `assert` / `cerr` の Submit 除去は脱糖に混ぜず、ビルドモードの処理として分ける
- 脱糖の実装は当面、規則ごとの手書き方式で続ける。規則をデータとして持ち汎用エンジンで適用する「規則エンジン方式」（仕様の記法がそのまま実装になる形）は、規則の数が増えたら再検討する（保留）
- **糖衣規則の表現は項書き換えの記法で書く**: 正規表現（文字列置換）では入れ子・評価順序・文脈を扱えないため採らない。仕様ではメタ変数（式・文・名前などの構文カテゴリ）を使った書き換え規則として記述し、実装は構文木のパターンマッチで規則と1対1に対応させる。テストは規則ごとに「入力 → 展開後」の対応で置く

## 速く書ける構文の候補（頻度順）

ほぼ全ての問題で使う層:

- 入力: `n = in`、`a, b = in`、`a = in[n]`、`a- = in[n]`（入力修飾子 `-` の正規形は `-= 1` への展開）
- 出力: `put x`、`put x, y`、`put a`（配列を空白区切りで出す形は採用方向）
- ループ: 上記の `for`
- 更新: 複合代入、`ans++`（正規形は `ans += 1`）、`a, b = b, a` の交換

頻出層:

- 連鎖比較 `a < b > c`（正規形は `and` で繋いだ形）
- 配列メソッド: `a.sum`、`a.len`、`a.min`、`a.max`、`a.sort`、`a.rev`、区間和、二分探索
- スライスと範囲: `a[1..]` など

## 決定: 辞書

- **辞書型を入れる**（v0 には無かった型を新設）。prelude のクラスとして実装し、コンパイラは汎用の仕組みだけを持つ（最小コアの原則どおり）
- **未存在キーは初期値で生やす**（defaultdict 式）: `cnt[x]++` のような数え上げがそのまま書けることを優先する。初期値の具体的な定義（型ごとの既定値をどこまで用意するか）は別途決める

## 決定: `<?=`（chmin / chmax）は入れない

- `x <?= y` の糖衣は採用しない。緩和は `x = min(x, y)` と書くか、更新の有無が要る場面では `if` を直接書く
- 判断の根拠: 関数風の正規形 `chmin(x, y)` は呼び出し元の変数を書き換える特殊形になり、コンパイラに専用の知識を持たせることになる。**できるだけコンパイラに頼らない**（汎用の仕組みとライブラリで済ませる）という方針を優先した

## 決定: セルフホスト向けプリミティブと Vec（step 59）

セルフホスト（コンパイラを spell 自身で書く）に向けた前提として、ドライバ層の機能を入れた。

- **公開 API は prelude の通常の関数・クラス**: `args() -> [str]`（`[0]` はプログラム名、C / sys.argv と同じ）、`read_file(path) -> FileData`、`write_file(path, text) -> bool`、`exit(code)`、`eprint(x)`（print の stderr 版）
- **失敗は `FileData { ok: bool, text: str }` で表す**: null も例外も入れない既定どおり。開けない・読み切れないとき `ok = false`、空のファイルは `ok = true` で `text = ""`
- **中身はコンパイラ組み込みプリミティブ `__spell_*`**: `[int]` の文字コード配列と `int` だけを扱い（`__spell_argc` / `__spell_argv_chars` / `__spell_read_file_chars` / `__spell_io_ok` / `__spell_write_file_chars` / `__spell_stderr_chars` / `__spell_exit`）、型検査に署名表を持ち、誤用は型つき・位置つきエラーにする。codegen は呼び出しをランタイムヘルパ（`__rt_spell_*`、libc のみ使用）への呼び出しとして出す。ヘルパの出力は step 63 以降、到達可能なプリミティブ呼び出しがあるものだけに限る
- **`exit` は prelude 関数にせず、型検査でプリミティブ呼び出しへ書き換える**: spell 関数のラベル `exit` が libc の `exit` と衝突し、ヘルパからの呼び出しが自分自身へ戻ってしまうため（print と同じ方式）。ヘルパ側も、利用者が同名関数を定義した場合に備えて libc の `exit` を名前で呼ばず、`fflush(NULL)` で stdio を流してから `_exit` で終わる（生成コードは atexit を登録しないので観測できる挙動は同じ）。stderr へは libc の `stderr` シンボルを参照せず、fd 2 への `write` で出す（NASM 変換でデータシンボルの extern が要らない）
- **`cerr` は `eprint` に統合**: 独立した cerr 構文は入れない。Debug / Submit のビルドモードを実装するときは、除去の対象を `eprint` として再検討する
- **`Vec<T>` を prelude に追加**: 末尾への追加が容量の倍増で均し定数時間になる伸びる配列。生成は Dict と同じく既定値ファクトリを受け取る。添字と `len` は論理長を見て、反復は開始時点のスナップショットに対するもの。なお、テストスイートの自作クラス `Vec`（2次元ベクトル）と名前が衝突したため、テスト側を `Vec2` へ改名した（prelude が名前を取る影響範囲の実例）

## 決定: 生成コードは到達可能な関数だけを含む（step 63）

- **出力は入口（`main` と `__spell_init`）から辿れる関数だけ**: codegen は出力前に AST を辿り、呼び出し・メソッド呼び出し・構築（`__init__`）・関数参照・ラムダの辺を集めて到達可能性を印付けし、印の無い関数はアセンブリへ出さない。prelude の未使用部分（Dict や Vec など）も落ちるため、提出用アセンブリが数千行から実用的な長さになる。ランタイムヘルパ（`__rt_spell_*`）も、到達可能なプリミティブ呼び出しに対応するものだけを出す

## 決定: Deque を prelude に追加（step 64）

- **`Deque<T>` を prelude に追加**: Queue と Stack を兼ねる両端キュー。中身は円環バッファ（先頭位置 `head` と要素数 `n`）で、容量の倍増時に直線化してコピーする。生成は Vec / Dict と同じく既定値ファクトリを受け取る
- **API**: `push_back` / `push_front`（戻り値なし）、`pop_back` / `pop_front`、`front` / `back`（覗き見）、`len`、添字は論理位置（`q[0]` が先頭）、反復は先頭から末尾へのスナップショット
- **空での pop / front / back は誤りで結果は不定**: 配列の範囲外アクセスと同じく検査はしない（境界検査は言語全体の未実装事項）
- **v0 との差**: 破壊的メソッドへの `!` 接尾辞は入れない。`q = deque` のような型推論による生成もせず、期待型＋ファクトリの既定どおりにする（矢印演算子は当初見送ったが、step 66 で dunder プロトコルとして入れた。後述）

## 決定: 配列を append で伸ばせるようにする（step 65）

2026-11-27 に本人が選択肢 A（配列自体を Python の list 風に伸ばせるようにする）を決定。実装方式は「実行速度 > 書き心地」の優先順位に従い、要素アクセスの速さを落とさない形にした。

- **容量ヘッダ方式**: 配列ブロックを `[cap][len][要素...]` に拡張する。要素0の位置と `len` の位置（要素0の8バイト手前）は従来どおりで、cap は16バイト手前。添字アクセスと `.len` の生成命令は変更前とバイト単位で同一（検証済み）。全ての生成経路（リテラル・`[fill; n]`・空リテラル・文字列リテラル・ランタイムヘルパーが作る配列）で cap = len に初期化する
- **`a.append(x)` は prelude メソッドではなく、型検査で組み込みノードへ書き換える**（exit の書き換えと同じ方式）。メソッドでは呼び出し元の変数を付け替えられないため。ユーザークラスが自分で定義した `append` メソッドは従来どおり使える（書き換えは配列型のレシーバだけ）
- **成長は realloc を使わず、malloc＋コピーで付け替える**: realloc はブロックが動くと別名（`b = a`）が宙に浮いたポインタになるため不採用。新しいブロックへコピーし、対象スロットにだけ新しいポインタを書き戻す。古いブロックは解放しない（言語全体の方針）。別名は古いブロックと古い長さを安全に見続ける
- **分裂の意味論**: 容量内（len < cap）の append は共有ヘッダの長さを増やすので別名・引数経由でも見える。容量超過の append は対象スロットだけを付け替えるので、別名と呼び出し側には伝わらない。作りたての配列は cap = len なので、初回の append は必ず付け替えになる
- **戻り値は新しい長さ（int）**: 配列自体は返さない（`a.append(x).append(y)` のような連鎖は、一時値への append がエラーになる仕様と矛盾するため）
- **対象はスロットを持つ場所だけ**: 変数・捕捉変数・フィールド・配列の要素。`(a + b).append(x)` や `f().append(x)` のような一時値は、書き戻す先が無いのでコンパイルエラーにする
- **評価順序**: 対象スロットのアドレスを1回だけ計算 → 値を評価 → スロットから現在のポインタを読み直す。内側 lvalue の規則として、`rows[0].append(f())` で `f()` が `rows` 自体を伸ばしても、外側の書き戻しは捕捉済みの旧スロットへ行く（lvalue は再計算しない）
- **反復中の append**: イテレータは開始時点のポインタを持ち、長さはそのブロックのヘッダを毎回読む。容量内の append は反復にも伸びが見え、成長した append の後はイテレータは旧ブロックの範囲をたどる（テストで固定）。古いブロックは解放されないので、どちらも壊れない

## 決定: 矢印演算子 `<-` / `->` は dunder プロトコルへの書き換え（step 66）

2026-11-27 に本人が「4つとも全て入れる。Deque なら pop/push、両方 int なら比較に、型で解決する」と決定。あわせて「演算子が通常メソッドを呼ぶのは気持ち悪い。dunder にして、通常メソッドは内部で dunder を呼ぶ形に」という設計原則の指摘があり、step 42 の dunder 書き換えの統一規則に揃えた。

- **実体は dunder プロトコル**: `__push_back__(v)` / `__push_front__(v)` / `__pop_back__()` / `__pop_front__()`。演算子は通常メソッドを直接呼ばず、この dunder へ書き換えられる。Deque の公開メソッド `push_back` 等は dunder を呼ぶだけの薄いラッパーにし、公開 API は不変。ユーザークラスが dunder を定義すれば、そのクラスでも矢印が使える（Deque 専用の決め打ちではない）。push 系 dunder の戻り値は self（コンテナ自身）
- **解決順（型検査で型により解決）**: `A <- B` は 1) `A.__push_back__(B)`、2) `A = B.__pop_front__()`（A は代入可能な対象: 識別子＝新規束縛も可・添字・フィールド。代入文の左辺規則と同じ）、3) 両辺が int なら比較 `A < (-B)`。`A -> B` は 1) `B.__push_front__(A)`、2) `B = A.__pop_back__()`、3) 両辺が int なら比較 `A > (-B)`。どれにも当たらなければ位置つきコンパイルエラー。比較形の右辺（符号反転される側）はノードを1回だけ使うので、評価はちょうど1回
- **ラムダとの曖昧性（`->` のみ）**: 裸の識別子 `x -> 式` は、x が現在のスコープで束縛済みなら矢印演算子、未束縛なら従来どおりラムダの引数名として解決する。束縛の有無はパーサの名前表（型検査が使う束縛構造そのもの）で判定する。帰結として、束縛済みの int 変数と同名の引数を持つ裸ラムダは書けなくなる（比較に解決される。ラムダが要れば `fn` 形で書く）。`(x, y) -> 式` と `fn` 形は形で区別できるので無変更。左辺が識別子でない式（`q[0] -> x` 等）は最初から矢印
- **連鎖はエラー**: `a <- b <- c` のように矢印同士をつなぐと、どちらの向きに結合しても意味が曖昧なのでコンパイルエラーにする
- **字句**: `<-` は2文字記号として、隣接している場合だけ結合する。`a < -b` のように空白があれば従来どおり `<` と単項 `-`（なお `a<-b` と詰めて書いても、両辺 int なら比較フォールバックで意味は同じになる）。優先順位は代入に準ずる低さで、右側は完全な式を取る
## 決定: ブロックは `:` ＋インデント形式も使える（step 67）

2026-11-27 に本人が決定（2026-11-25 の「いったん今のまま（`{}` のみ）」という棚上げを覆す）。`{}` は見た目がすっきりしないため、`:` 形式を正規形とし、`{}` も併用可とする。

- **両形式の併用**: ブロックは箇所ごとに独立に選べる。文の頭の直後が `{` なら波括弧ブロック、`:` ならインデントで範囲を決めるブロック（suite）。同じファイル・同じ入れ子の中で混在してよい
- **対象**: `def`、`class`、`if` / `elif` / `else`、`while`、`for`（for...else を含む）、`@` 系の糖衣が取るブロック。ラムダ `fn(...) { }` の本体は `{}` のみ（式の内側にインデントを持ち込まない）
- **suite の形**: `:` の後に改行し、より深くインデントされた文の並びがブロックになる。`:` の同じ行に文を1つ書く1行形も可（`if (x == 0): return 0`、`def f(): return 1`、クラスも `class P: x: int` のように同じ行にメンバを並べられる）
- **空の suite は位置つきコンパイルエラー**（Python と同じ。`{}` の空ブロックは従来どおり可）
- **インデントの数え方**: 行頭の空白を列で数え、空白は1列、タブは次の8の倍数の列まで進める（Python と同じ）。空行とコメントだけの行は判定に使わない。dedent が既存のどの段にも一致しない場合は、位置つきエラー（「インデントが揃っていません」）
- **実装方式**: INDENT / DEDENT トークンは字句側で出さず、パーサ側でトークンの行番号と行頭の空白から段を判定する。spell では深さ0でも演算子の後などで式が改行をまたいで続く（step 55）ため、論理行の終わりは字句側だけでは決められず、文の完了を知っているパーサに合わせて段を見るほうが既存の書き方を壊さないため。段は suite ごとの再帰で持つ
- **for の頭の `:` の曖昧性**: 反復対象への型注釈（`for i in x: [int] = [7, 8]`）は従来どおり使える。その位置では、式の直後の `:` は「型 = 」と続く場合だけ注釈として扱い、それ以外は suite の区切りとする。型の名前が実在することも条件にするため、suite の最初の文が `名前 = ...` という代入でも、その名前が型でなければ注釈と誤認しない
- prelude.sp は `{}` のまま書き換えない

## 決定: if / elif / while の条件の括弧は任意（step 69）

2026-11-27 に本人が決定。`:` 形式を正規形とする流れで、条件を囲む括弧も見た目をすっきりさせるため外せるようにする。

- **括弧は任意**: `if cond:` / `while cond { }` と書ける。従来の `if (cond) { }` もそのまま使える（prelude・既存コードは括弧形のまま）
- **対象**: `if` / `elif` / `while` の条件のみ。それ以外の括弧（関数呼び出し・ラムダ・型注釈など）は無変更
- **実装方式**: 条件は通常の完全な式として読み、終わりはブロックの開始（`{` か `:`）で判断する。括弧形は primary の括弧式としてそのまま読めるため、特別扱いは要らない。`if (a + b) * 2 > 3:` のように括弧式で始まる条件も、括弧を条件全体と誤認せず最後まで読む。直後の `:` が suite の区切りと競合する点は for の頭と同じで、型注釈の `:` は「型 = 」と続く場合だけ注釈として扱う（`cond_expr` が `suppress_anno` を立てる）
- **改行規則**: 条件も式文と同じ規則に従う（step 55）。演算子を行末に置けば次の行へ続けられ、括弧形では括弧の中は従来どおり改行自由

## 決定: 真理値リテラル `true` / `false` / `T` / `F`（step 70）

2026-11-27 に本人が決定。それまで spell に真理値リテラルはなく、`true` などは未束縛の識別子として読まれていた（bool 値は比較式などからしか作れなかった）。

- **4つの綴り**: 式の位置で `true` と `T` は真、`false` と `F` は偽のリテラルになる。`T` / `F` は短縮形。型は prelude の bool クラスで、実行時の値は従来の bool と同じ 1 / 0（比較結果ともそのまま混ぜられる）
- **実装方式**: トークナイザのキーワードにはせず、パーサの式（primary）の識別子解決でこの4綴りだけをリテラルノード（ND_BOOL）に変換する。typecheck は bool 型を返し、codegen は数値リテラルと同じ定数を出す
- **型の位置は無関係**: 型注釈・型パラメータ宣言・クラス名などの位置は primary を通らないため、`class Vec<T>` の `T` のような型パラメータ名は従来どおり名前として読める。メンバ名の位置（`obj.T`）も同様に対象外
- **帰結**: `true` / `false` / `T` / `F` という名前の変数は式の位置では作れない（代入先にすると「`true`には代入できません」のコンパイルエラーになる）。特別な救済は入れない
## 決定: 文頭 `<` の出力糖衣を削除する（step 71）

2026-11-27 に本人が決定。step 48 で `< "hello world"` を書けることを目標に導入した糖衣だが、比較演算子 `<` と見た目が紛らわしいため削除する。

- **文頭 `<` は削除**: 文の頭の `< 式;` は通常の構文エラーになる（特別なエラーメッセージは設けない）
- **`<<` は残す**: `<< 式;` は引き続き print の糖衣として使える
- **ドキュメントの例文**: リファレンスと糖衣集のコード例は、文終端のセミコロンを付けない正規形（`:` 形式・セミコロンなし）の見た目に揃える（同じ行に文を並べる箇所の区切りは除く）
## 決定: 文字列入力は `>>>`、入力対象に個数形と空白区切りを追加（step 72）

2026-11-27 に本人が決定。文字列も `>>` 系の記号で読みたいという要望に対し、「対象の型で読むものを解決する」案は、str 変数を事前に宣言する分だけ記述量が増えるため不採用となり、記号で区別する案が選ばれた。

- **`>>>` は文字列トークン入力**: `>>> 対象;` は `対象 = in_str;` と同じ（空白区切りのトークンを1つ読んで str として代入する）。対象の形と複数対象は `>>` と同じ。行読みは従来どおり `s = in_line;` の担当で、`>>>` はトークン読みのみ
- **字句とジェネリクスの整合**: `>>>` は3文字記号として字句で1トークンにする。型注釈の閉じ括弧は既存の分割方式（`>>` を1つ消費して残りを次の閉じ括弧に回す）をそのまま伸ばし、`Vec<Vec<Vec<int>>>` の `>>>` を1つずつ消費する。型の試し読み（scan_type）でも `>>>` は深さ3として数える
- **個数形 `>> a[n]` / `>>> s[n]`**: 次の展開と等価な糖衣。個数式は対象の処理時点で1回だけ評価する
  ```
  a = [0] * n
  @n >> a[i]   （i は 0..n-1 のループ変数）
  ```
  （`>>>` 形は `[0]` が `[""]` になる）。`>> n, a[n];` のように、左から順に処理して既に読まれた個数を使う複合形が本命の用途。n = 0 なら空配列。負数などの振る舞いは展開形（`[0] * n` と `@n` ループ）の振る舞いと一致する
- **添字形との振り分け規則**: 対象の基底名がその時点で**未束縛**なら個数形、**束縛済み**なら従来の添字形（既存配列の1要素へ1つ読む）。例: `a = [0] * 5; >> a[2];` は添字形、`>> n, a[n];` の a は未束縛なので個数形。束縛の判定はパーサの名前表（矢印の振り分けと同じ仕組み）で行う。個数形の対象は識別子のみ（フィールドや添字を基底にはできない）
- **空白区切り**: 対象はカンマ区切りに加えて空白だけでも並べられ、混在もできる（`>> x y;`、`>> x, y z;`、`>> n a[n]`）。空白区切りの継続は同じ行の中だけとし、次の行の先頭の識別子を対象として飲み込まない（行をまたぐ継続はしない。セミコロン省略の規則と整合させる）

## 決定: 文頭の `?` は if の糖衣（step 73）

2026-11-27 に本人が決定し、意味を明確化した。`?` は三項演算子（`条件 ? 式1 : 式2`）ではない。文頭に置く if 文の開始記号の別名として導入する。

- **形**: `? 条件 ブロック` が if 文そのものになる。後続の elif / else はキーワード形でも、`|` 形（step 74）でも受けられる
- **意味論は if と同一**: 条件の括弧は任意、ブロックは `:`＋インデント形式と `{}` 形式の両対応。内部的には通常の if 文と同じノード（ND_IF）になる
- **使える場所**: 文の頭だけ。式の中の `?` は定義せず、現れたら通常の構文エラーになる
- **実装方式**: トークナイザに `?` を記号として追加し、パーサの文の振り分け（stmt）で `?` を通常の if 文の解析（stmt_if）へそのまま流す

## 決定: `|` を else / elif の糖衣にする（step 74）

2026-11-27 に本人が決定。旧 spell_v0 にあった糖衣の移植（v0 の parser は `Token::Else | Token::Pipe` を受け付けていた）。

- **振り分け**: if 文の後に `|` が来たら、直後がブロック開始（`:` または `{`）なら else、式が続けば elif として読む。`else` / `elif` キーワードと完全に等価で、混在もできる（`elif` の後に `|:`、`|` の elif の後に `else` など）
- **for...else**: for（反復形・回数形・`@` リピート）の else も `|` で書ける（v0 と同じ）
- **ブロック形式**: 既存の else/elif と同じく `:` インデント形式・`{}` 形式の両対応。1行 suite の後にも置ける
- **式の中では使わない**: `|` は演算子としては定義しない（ビット和は spell に無い）。if / for の後以外の場所に現れたら通常の構文エラーになる
- **実装方式**: 字句では `|` を記号として追加する（`||` の直後に置き、論理和の照合を壊さない）。パーサでは stmt_if の else/elif 判定と for の else 判定（make_for_iter / make_for_count）に `|` の分岐を足すだけ

## 決定: 個数形を n 次元に一般化する（step 75）

2026-11-27 に本人が決定。step 72 の個数形は一次元のみで、`>> a[n][n]` はコンパイルエラーだった。これを一般化する（「二次元まで」で打ち切るより、再帰的な1つの規則にするほうが恣意的でない、という判断）。

- **形**: 入力対象 `>> a[d1][d2]...[dk]`（k ≥ 1、基底名が未束縛の場合）は個数形として、d1 × d2 × … × dk の入れ子配列を作り、行順（最も右の添字が最速）に全要素を読む。`>>>` は str 版で同じ。直方体のみ扱い、ギザギザ配列は対象外
- **展開の意味論**: 個数式は対象の処理時点で左から順にそれぞれ1回だけ評価し、一時スロットへ入れる。配列は再帰的に作る: 最外は `[雛形] * d1`、各段のループの中で枠ごとに `[雛形] * d(j+1)` で新しい小配列を割り当ててから中を読む。小配列を行同士で共有（別名化）しない（prelude の read_ints2 が「外側を作ってから各行を新しい配列で置き換える」方式なのと同じ作り方）
- **振り分け規則は不変**: 基底名が未束縛なら全ての角括弧が個数、束縛済みなら全て従来の添字（1要素だけ読む）。混在形は作らない。角括弧の継続は、空白区切りの対象継続と同じく同じ行の中だけ
- **次元 0**: いずれかの個数が 0 なら、その方向は空配列になり、その部分については何も読まない（`>> a[0][3]` は長さ 0、`>> a[3][0]` は空行が3つ）

## 決定: 構築の簡略化（step 76）

2026-11-28 に本人が決定。`q: Deque<int> = Deque(zero_int)` の形が「ファクトリを渡す」「要素型を注釈で教える」の両面で煩雑だという指摘（「タイプ数が多すぎる」）から、3点セットで簡略化する。

- **構築時の明示的な型引数（一般機能）**: ジェネリッククラスの構築で `名前<型, ...>(引数...)` と書ける（`Deque<str>()`、`Vec<int>()`、`Pair<int, str>(...)`、`Dict<str, int>(zero_int)`）。入れ子（`Vec<Vec<int>>`）も可。型引数は構築呼び出し専用で、呼び出しなしで式の位置に `名前<型, ...>` と書く形は追加しない。個数がクラスの型パラメータ数と合わない場合と、期待型があるのに型引数と矛盾する場合は位置つきエラー
- **優先順位**: 明示的な型引数 > 期待型（注釈・関数の引数位置・戻り値の型） > 既定（下記）。`__init__` の引数からの推論は従来どおり先に試すが、明示的な型引数があればそちらで上書きする
- **Vec / Deque の引数なし構築**: 埋め草のファクトリは要素型の既定値で補う（int → `zero_int`、bool → `zero_bool`、str → `zero_str` への関数参照を、利用者が手で書いた場合と全く同じ形で合成する）。Dict と違い、Vec / Deque のファクトリ値はバッファの埋め草でしかなく外から観測できない（読み取りは論理長の範囲だけ）ため、既定で補っても意味論は変わらない。従来形 `Deque(zero_int)` は無変更で動く
- **要素型の既定 int（Vec / Deque のみ）**: 明示的な型引数も期待型も無い場合は、要素型を int とする（`q = Deque()`、`q = Deque(zero_int)`）。Dict のファクトリは無いキーの初期値として観測できる意味論を持つため、この既定は Dict や一般のジェネリッククラスには広げない。Dict の引数なし構築も追加しない（ただし型引数の明示は一般機能として効くので、`Dict<str, int>(zero_int)` は注釈なしで書ける）
- **自動で補えない要素型**: 要素型がクラスの場合は「要素型がクラスの場合はファクトリを渡してください」という位置つきエラーにする。配列型・関数型の要素も、既定値を返す prelude 関数（`zero_*`）が無いため同じくファクトリを要求する（判断の記録: 自動で補えるのは `zero_*` 関数がある int / bool / str だけ、という線引き。空配列リテラルはパース時にフレームの置き場所を確保する作りで、型検査での合成ができない）
- **実装方式**: パーサは primary で「クラス名（変数に隠れていないもの）＋ `<` ＋型の並び＋ `>` ＋ `(`」をトークン列の先読みで判定してから、型注釈と同じ parse_type で型引数を読む（`>>` の分割もそちらに任せる）。型検査は check_construct で、明示的な型引数の検証 → 期待型の適用 → 既定 int → 実体化の順に処理し、引数なし構築のファクトリ補完は実体化後の要素型に対して行う

## 決定: Pos2 / Pos3 と型を引数に渡す構築（step 77）

2026-11-28 に本人が決定。グリッド探索（BFS など）で座標を扱うための導入。当初は行列クラス Mat とメソッドのオーバーロードも検討したが、本人判断で見送り（必要になったら再検討する）。

- **Pos2 / Pos3（prelude の通常クラス）**: フィールドは Pos2 が x, y、Pos3 が x, y, z（すべて int）。dunder は `__add__` / `__sub__`（要素ごと）、`__mul__`（int とのスカラー倍）、`__eq__` / `__ne__`、`__hash__`（配列と同じ流儀: h=5381 から h=h*33+要素）、`__getitem__`（0 始まり、x が 0）、`__str__`（空白区切り "1 2" / "1 2 3"）。prelude 関数 `zero_pos2()` / `zero_pos3()` を追加し、step 76 の埋め草テーブルにも載せたので `Deque<Pos2>()` や `q: Deque<Pos2> = Deque()` が引数なしで構築できる。Dict のキーとして使える（`Dict<Pos2, int>`）
- **リテラル `(1, 2)` / `(1, 2, 3)`（糖衣）**: 式の位置のカンマ区切り括弧リストは、要素2つで Pos2、3つで Pos3 の構築に読み替える。要素は任意の式。4つ以上は位置つきエラー。`(式)` は従来どおり括弧式で、`(a, b = 1, 2)` のような括弧つき複数代入も従来どおり（括弧内に単独の `=` があれば複数代入として読む）。`(x, y) -> 式` のラムダとの振り分けは従来どおり（`->` が続けば引数リスト）
- **`a[p]` 添字の糖衣**: 添字の型が Pos2 / Pos3 のとき、型検査で `a[p[0]][p[1]]`（Pos3 は3段）へ書き換える。対象は配列だけで、深さは Pos の次元で決まり、配列の入れ子の深さと一致しない場合は位置つきエラー。p は一度だけ評価する（パース時に確保した一時スロットへ退避し、代入式を最初の要素取り出しのレシーバとして埋め込む）。代入形 `a[p] = v` も同じ書き換えで効く。Dict のキーアクセス `d[p]` は従来どおり `__getitem__` へ行く
- **型を引数に渡す構築**: `Deque(int)`、`Vec(str)`、`Deque(Pos2)`、`Deque([int])` のように、構築の引数がちょうど1つで型として解釈できる場合は「要素型の指定＋ゼロ値ファクトリの自動生成」として扱う。対象は Vec / Deque のみ（Dict は値の型だけではキーの型が決まらないため対象外。`Dict<str, int>(...)` のような全体が決まる形は step 76 の型引数で既に書ける）。振り分けは構文的: クラス名が変数に隠れていないこと、引数が型として読み飛ばせて直後が `)` のこと。ただし引数が単独の識別子で変数として解決される場合は式として扱う（ファクトリを収めた変数を渡す形を壊さない）
- **ゼロ値の合成規則（再帰）**: int → 0、bool → false、str → ""、[T] → 新しい空配列、Pos2/Pos3 → ゼロ値、ユーザークラス → `__init__` の引数がすべて再帰的にゼロ化可能ならそれらをゼロで埋めた構築（`__init__` が無ければ引数なし構築）。関数型・型変数・注釈のない引数はゼロ化できず、「ゼロ値は自動で作れないため、ファクトリを渡してください」という位置つきエラーにする。自己参照クラス（`__init__` の引数に自分自身が現れる形）は有限の構築ではゼロ化できないため対象外（配列を挟めば空配列で断てる）。クラスのゼロ化可能性はフィールドではなく `__init__` の引数の型で判定する（通常のフィールド代入型 `__init__` では一致する）。なお、この再帰合成は型を引数に渡す構築だけの話で、step 76 の引数なし構築の線引き（自動で補えるのは `zero_*` のある型だけ）は不変
- **ゼロ値の合成経路**: step 76 の知見（型検査の段階で配列リテラルを合成すると置き場所が割り当てられない）に従い、配列・文字列のリテラルノードは合成しない。int / bool / str / Pos2 / Pos3 は prelude の `zero_*` 関数参照で済ませ、それ以外は「ゼロ値の式を返す合成ラムダ」を関数チェーンへ足して通常のラムダとして検査・生成する。式の中の配列は prelude の `zero_array()`（`[]` を返す、戻り値の要素型は推論で [unknown] になり任意の [T] と緩く一致する）呼び出しで代用し、文字列は `zero_str()` 呼び出しで代用する（数値・真理値の葉ノードは置き場所を必要としないため合成する）

## 決定: 条件の真理値プロトコル `__bool__` と未定義変数のエラー化（step 79）

- **真理値プロトコル**: if / elif / while / `?` の条件位置と、`!` / `&&` / `||` の被演算子では値を真理値として解釈する。bool はそのまま、int は 0 でないこと（従来どおり）。クラス・配列・文字列は、その型に `__bool__() -> bool` が定義されていれば、型検査で `x.__bool__()` への呼び出しに書き換える。`__bool__` が無いクラスを条件に使うのは位置つきコンパイルエラーにする（ポインタの真偽で常に真になる従来の振る舞いはやめる）
- **prelude の `__bool__`**: 配列・str・Vec・Deque・Dict に追加し、いずれも「長さが 0 でないこと」とする。Pos2 / Pos3 には付けない（座標の真偽に意味は無いので、条件に使えばエラーになるのが正しい）
- **未定義変数の読み取りはエラー**: ローカル変数・グローバル変数・関数・クラス・組み込み・prelude の名前のどれにも当たらない読み取りは、位置つきコンパイルエラーにする。定義の判定は、プログラム全体（グローバル）・関数全体（ローカル）の代入の存在で行い、文同士・文内での前後関係は見ない。したがって、後方で代入されるグローバルを関数から読む前方参照は従来どおり動く（パース時点でローカルとして解釈された読み取りは、型検査で同名の定義済みグローバルがあればグローバル変数として読み直す）
- **typo の候補**: 「エラー出力」の決定に従い、未定義変数のエラーに限って、参照できる変数の中に編集距離の近い名前が1つだけ突出してあれば「ヒント: もしかして `名前` ですか（定義は N 行目）」を添える。短い名前ほど許容距離を厳しくし（長さ2以下は距離1まで、5以下は2まで、それ以上は3まで）、最良と次点の差が1以下（同率・僅差）なら出さない。最大1件

## 決定: while の糖衣 `@?`（step 80）

2026-11-28 に本人が決定。`@ x` は既に「x 回ループ／x の反復」の意味を持つため、素の `@` で while を兼ねると「x 回」と誤認する危険がある。そこで条件の印 `?`（if の糖衣と同じ印）を足し、`@?` を while の糖衣とする。

- **形**: 文頭の `@? 条件:` または `@? 条件 {}` で、`while 条件:` / `while 条件 {}` と完全に同じ意味。本体は `:` 形式・`{}` 形式の両方、1行スイートも可。実装は stmt() の `@` 分岐で `{` / `:`（無限ループ形）の判定より前に `?` を判定し、通常の while（stmt_while）にそのまま流す。したがって条件の読み方（括弧任意・step 79 の `__bool__`）、break / continue、エラー（条件直後の `?` の拒否を含む）は全て通常の while と同一
- **`@` 単独の意味は不変**: `@n`（回数）、`@{}` / `@:`（無限ループ）、`i@n`（カウンタつき回数）、`x@a`（要素走査）は従来どおり。`@` 族の中で「条件で回す」形だけが `@?` になる
- **while...else は対象外**: spell の while に else は無いので、`@?` への `|` 連鎖は特別な対応をしない

## 決定: 配列メソッド sort / sorted / sum / min / max / count（step 83）

2026-11-28 に本人が決定。ドッグフーディング（過去の ABC 10問を spell で解く実地評価）で「配列の sort が無い」「min / max が無い」が不足の筆頭に挙がったことを受けた追加。全て prelude の `array<T>` のジェネリックメソッドとして実装し、コンパイラは型ごとに特別扱いしない。

- **適用条件は dunder で統一**: sort / sorted / min / max は要素型に `__lt__`、sum は要素型に `__add__`、count は要素型の `==`（`__eq__` があればそれ、無ければ同一性フォールバック）を要求する。要求を満たさない要素型で呼ぶと、実体化時の型エラーになる
- **`sort()`**: インプレースの昇順ソートで、戻り値はない。**安定ソートではない**。実装は median-of-three ピボットのクイックソート（Hoare 分割）＋小さい区間（12要素以下）は挿入ソート。分割後は小さい方へだけ再帰し大きい方はループで続けるため、スタック深さは log n 程度に収まる
- **`sorted()`**: ソート済みの新しい配列を返すコピー版。元の配列は変更しない。中身のコピーを作って `sort()` する（中核処理は共有）
- **`sum()`**: 最初の要素から `+` で畳み込み、戻り値は要素型 T そのもの。[str] では全文字列の連結、[Pos2] では成分ごとの合計になる。prelude 内では要素型のゼロ値を合成できないため、**空の配列での sum() は未定義**（min / max と同じ線引き）
- **`min()` / `max()`**: `<` で比較した最小・最大の要素。**空の配列では未定義**（Deque の空 pop と同じ線引きで、検査はしない）
- **`count(v)`**: v と等しい要素の個数を int で返す（Python の list.count と同じ意味）。len とは別物
- **str の順序**: prelude の str に辞書順（文字コード順）の `__lt__` / `__le__` を追加した。これで [str] の sort / min / max が動く。共通部分が等しければ短い方が小さい
- **Pos2 / Pos3 の順序**: 辞書順（x、次に y、次に z）の `__lt__` / `__le__` を追加した。座標のソート・min / max に使う。これにより [Pos2] は配列メソッドの要求 dunder を全て満たす
- **性能**: sum / min / max / count はイテレータやメソッド呼び出しを経由せず、直接添え字アクセスのループで書く。実測（ランダム [int] 10^6 件、同セッション・最小値）: sort は生成込み 274ms に対し C の qsort（-O2）が 243ms で約 1.1 倍。sum+min+max+count の4パスは生成を引いて約 10ms、C の同等ループ約 3.3ms（3パス）で、1パスあたり約 2.3 倍（コード生成の差であり、アルゴリズムの差ではない）

### 付随するコンパイラ変更: 実体化メソッドの遅延検査

- **問題**: 従来は、ジェネリクスを実体化するとそのクラスの全メソッドが型検査された。そのため配列に sort（要素型の `__lt__` を要求）を足すと、`[bool]` の表示や `[[int]]` の反復、__lt__ の無いクラスの配列への count() など、無関係な呼び出しまで「`<` が定義されていません」で失敗するようになった（実測で確認）

- **帰結**: dunder の要求は「そのメソッドを呼んだとき」にだけ効くようになった。これは今回の5メソッドに限らず従来からの要求（array の `__hash__` が要求する要素型の `__hash__` など）にも同じく当てはまる。呼ばれないメソッドの本体エラーは、CLI でも LSP でも報告されなくなる
## 決定: 安全添え字 `a?[i][j]`（step 81）

2026-11-28 に本人が決定。spell_v0 の `Expr::SafeIndex` の移植で、意味論は v0 と同一にする。きっかけは step 78 のバグ2（`if a?[0] == 10:` が飲み込まれて静かに違う意味になっていた）で、その記録は「安全添字は未実装」という前提に立っていたが、本 step で実装したため前提が変わる: 同じ書き方は今度は安全添え字として正しく解釈され、step 78 の拒否（条件の直後の `?` のエラー）は `[` を伴わない `?` に対してだけ残る。

- **意味論**: 単独で書くと bool（連鎖の全段とも 0 <= 添え字 < その段の長さ のとき真）。比較（==, !=, <, <=, >, >=）の直接の被演算子として書くと、どこかの段で範囲外なら比較全体が false（`!=` でも false）、全段範囲内なら要素同士の通常の比較になる。それ以外の位置（算術の中など）では bool 形として扱い、型の不一致は通常の型エラーになる。対象と各添え字はちょうど1回だけ評価し、範囲チェックは浅い段から順に短絡させる（深い段の長さを読むのは、浅い段の範囲内が確定してから）。負の添え字は全段で範囲外
- **対象**: 配列と str だけ。Dict や `__getitem__` を持つクラスは長さの契約が無いため対象外とし、位置つきエラーにする
- **str の段の要素**: 安全添え字と Pos 添字の展開の中でも、文字列の段は通常の `s[i]` と全く同じ `__getitem__` 経由とし、要素の型はその戻り型に従う（コンパイラ側で int 前提の特別扱いはしない）。`s[i]` の戻り型は文字コードの int から1文字の str へ変更する予定が別途あり（後続 step で prelude を変更）、変更後は `s?[np] == "."` のようなグリッドの文字比較がそのまま成立する。本 step のテストは str 要素の値を固定せず、範囲チェックの bool 形と範囲外で比較が false になる形で確認し、`s?[np] == "."` を使う io テストは変更側の step で追加する
- **Pos 添え字**: `a?[p]`（p は Pos2 / Pos3）は step 77 の `a[p]` と同じ展開を安全化したものとして扱う。加えて通常形にも効く修正として、末尾の str をもう1段として数える: 要素型が str の配列（[str]）への Pos2 アクセス `s[p]` / `s?[p]` は「行 = s[p[0]]、文字 = 行[p[1]]」として扱い、安全形では文字列の長さも範囲チェックに含める。通常形 `s[p]` の深さ不一致エラーはこの形については解消される
- **禁止形**: 代入先に使うのは位置つきコンパイルエラー（複合代入・複数代入・入力対象も同じ）。連鎖比較（`0 < a?[0] < 3`）の中に現れる場合も位置つきエラーにする（ガードの仕組みを連鎖へ広げるより、まず明示的に禁止する。黙って bool として比較される形は作らない）

## 記録: 安全添え字のバグ調査と `[fill; n]` の行共有の修正（step 82）

2026-11-28。step 81 と step 84 のマージ後検証で「利用者の BFS イディオムが segfault する／数え上げが合わない」と報告された件の調査結果。当初の仮説（一時スロットの衝突）は**外れ**で、安全添え字そのものに欠陥は無かった。切り分けの結論は次の3点。

- **数え上げの不一致は仕様どおり**: 検証用プログラムが Pos を (x, y) のつもりで書き、配列を [h][w] の形にしていた。添え字糖衣の成分順は step 77 の決定どおり `a[p] = a[p[0]][p[1]]`（第0成分が外側＝行）で、t077 / t078 がこの順を固定している。(x, y) で扱いたい場合は `a[p.y][p.x]` のように成分を明示する。検証用プログラムの開始セル (3, 0) は 3 行の盤では盤外であり、正しい数え上げは 3
- **segfault は通常添え字の範囲外読み**: 検証用プログラム末尾の `dist[goal]`（goal = (w - 1, h - 1) = (3, 2)）が 3 行しかない配列の行 3 を通常添え字で読んでいた。通常添え字の範囲外アクセスは従来どおり未定義動作（だからこそ安全添え字がある）。当該行を除けばプログラムは正常終了する
- **本物の欠陥: `[fill; n]` が配列リテラルの fill を全スロットで共有していた**: `gen_newarray` は fill を1回だけ評価し、同じ値を全スロットへ書いていた。fill が配列リテラルの形だと全要素が同じ配列オブジェクトになり、`[[-1; w]; h]` の行が全て同一になって、1行への書き込みが全行へ伝播する。step 75 の個数形が「小配列を行同士で共有しない」と明記したのと同じグリッド構築の線引きが、fill 形では守られていなかった
- **修正**: fill が配列リテラルの形（ND_ARRAY / ND_NEWARRAY）の場合に限り、fill は従来どおり1回だけ評価し、各スロットへ構造の複製を入れるようにした（ランタイムヘルパ `__rt_spell_copy_array`。配列ブロックを入れ子の深さまで複製し、cap = len で作り直す。深さは fill の型から決める）。リテラルでない fill（変数・呼び出し結果）は従来どおり同じ値を共有する（`[row; 3]` は row そのものを3つ並べる）。クラスインスタンスなどの非配列の要素は複製の対象外で、複製されるのは配列ブロックだけ
- **ついでに直した負の長さ**: Luna のレビューで発覚。`[fill; n]` は n が負だと確保サイズの計算が不足し、ヘッダの書き込みが確保領域を超えていた（リテラルでない fill の従来パスでも segfault を実証）。両パスとも、負の長さは 0 に丸めて空配列として扱うようにした

## 決定: スライスと文字列メソッド第1弾（step 85）

2026-11-28 に本人が決定。

- **部分文字列はスライスで表現する**（`substr` メソッドは作らない）: `x[i:j]` は Python 式のスライスで、i 以上 j 未満の部分を**新しい** str / 配列として返す（元の値は変えない）。端の省略可（`x[i:]`、`x[:j]`、`x[:]`）、負の添え字は末尾から数え、範囲外は端に丸め、`j <= i` なら空。ステップ `x[i:j:k]` は入れない。対象は配列と str のみ
- **実装**: parse の後置添え字で ND_SLICE を作り、typecheck が境界を正規化（省略→0/len、負→+len、[0, len] に丸め、hi < lo なら hi = lo）してから prelude の `__slice__(lo, hi)` を呼ぶ形に書き換える。対象と境界は1回だけ評価して一時スロットへ退避する。`__slice__` は str と array<T> の両方に prelude で実装し、正規化済みの境界だけを受ける。スライスへの代入は位置つきエラー、安全添え字 `a?[...]` の中でスライスを使う形も位置つきエラー（対象外）
- **角括弧内の `:` の扱い**: 添え字式を読む `assign()` は通常 `:` を型注釈として消費するため、角括弧内（通常添え字・安全添え字とも）では条件式と同じく `suppress_anno`（先読みで「型 = 」が続く場合だけ注釈とみなす）に切り替える。これで `a[x: int = 3]` のような注釈つき代入を添え字に書く従来の形も壊れない
- **対象の型が分からない場合**: 期待型（注釈つき代入の右辺など）が配列か str ならそれを採り、それ以外は位置つきエラーにする（型注釈での明示を促す）。無注釈の引数へのスライスはこの形になる
- **文字列メソッド第1弾**（prelude の str）: `starts_with(t)` / `ends_with(t)`、`find(t)`（無ければ **-1**、空の t は 0）/ `contains(t)`、`split(sep)`（Python の str.split(sep) と同じく連続・端の区切りで空文字列を含む。sep が空文字列なら分割せず自分だけの配列）、`sep.join(a)`、`to_int()`（atoi 式: 先頭の空白と符号を読み、数字以外で止まる。数字が無ければ 0）
- **負の長さのリテラルはコンパイルエラー**（step 85 の追加決定）: `[fill; n]` の長さと、入力の個数形 `>> a[n]` / `>>> s[n]`（n 次元形の各次元を含む）の個数が、リテラルだけからなる定数形（整数リテラル、単項マイナス、リテラル同士の + - *）で負になる場合は、位置つきコンパイルエラーにする。step 82 で入れた「負の長さは実行時に 0 に丸める」扱いは、変数など実行時に決まる負数に限って維持する（静的に分かるものは早く落とす、という線引き）。判定は parse 時（expr.c の `const_int_value`）

## 決定: 添え字の回り込み（step 86）

2026-11-28 に本人が決定。速度への影響を実測し、影響が大きい場合は代替案を検討する前提で導入した。

- **通常の配列添え字 `a[i]` は実効添え字を `i % len` として扱う**（読み・代入・複合代入・append の対象のいずれも）: 剰余は spell の `%` と同じ Python 式（負数でも 0 以上）なので、`a[-1]` は最後の要素、`a[len]` は先頭、`a[len + 1]` は2番目を指す。入れ子の配列では段ごとに、座標添え字 `a[p]` では成分ごとに回り込む
- **対象外**: 安全添え字 `a?[i]` は従来どおり厳密な範囲チェック（範囲外は false）のまま。クラスの `__getitem__`（Dict / Vec / Deque / str / ユーザークラス）とスライスの境界正規化も変えない

- **長さ 0 の配列・空文字列への添え字は従来どおり未定義**: 余りが取れないため、生成コードは長さ 0 のとき剰余を取らず素通りする（0 除算で落とさない）
- **実装**: codegen の `gen_index_addr`（ND_INDEX のアドレス計算の唯一の経路。読みは gen_index、代入系は gen_addr 経由で全てここに集まる）で、レシーバの型が TY_ARRAY の場合だけ、長さ（要素0の8バイト手前）を読み、0 でない場合に step 53 の `emit_divmod_adjust` を再利用して Python 式の剰余を適用する。型不明のレシーバには適用しない（従来どおり緩く通す）

## 決定: 診断の網羅（step 88）

2026-11-28。本人の方針「変な書き方をコンパイルで通さない」に基づき、検査の穴を塞いだ。変なプログラムはアセンブラエラー・リンクエラー・コンパイラの異常終了・無言の誤答に漏らさず、位置つきのコンパイルエラーで止める。

- **未定義の関数呼び出しはエラー**: 定義の無い関数呼び出しは従来「型不明」として通り、リンクエラーに漏れていた（例: `min(3, 5)`）。型検査で「関数`X`は定義されていません」とし、step 79 の変数版と同じ基準で typo の候補も出す（候補は通常関数のほか、外部関数・`print` / `eprint` / `exit`。関数には定義位置が記録されていないため行番号は出さない）。**定義なしで呼べる外部関数は署名表で許可する**: prelude・suite・ドキュメントの例の「定義なし呼び出し」を全数調査した結果、該当は8個だけだった — libc の `getchar`（0引数→int）・`putchar`（int→int）・`fflush`（int→int、テスト suite が使用）と、tests/funcs.c の C 側ヘルパ `ret3` / `add` / `sub` / `add6` / `sub6`（いずれも int のみ）。この8個は引数の個数と型も照合する。ユーザーが同名の関数を定義した場合はそちらが優先される（従来どおり）
- **型が分からない値へのメソッド・フィールドはエラー**: 未注釈の引数など型不明のレシーバへのメソッド呼び出しは、メソッド情報が無いままコード生成へ進みコンパイラが落ちていた（フィールド読みも壊れたコードを生成していた）。型注釈で明示するよう案内する位置つきエラーにした（step 85 のスライスの文面と同形式）。`len` プロパティだけは従来どおり型不明でも使える
- **型が分からない値と配列の `==` で落ちない**: 配列比較への書き換えが、左辺が型不明のときに無いメソッドを参照してコンパイラが落ちていた。左辺が配列でない（型不明を含む）場合は書き換えず通常の比較として扱う。なお `[1, 2] == 未注釈関数の結果` のように配列のメソッドへ書き換わる形で右辺が型不明の場合は、従来の「型不明は緩く通す」方針の範囲で、生成プログラム側の未定義動作として残る（コンパイラ自体は落ちない）
- **異型同士の `==` / `!=` はエラー**: 両辺とも型が判明していて相容れない場合（int と str、int と配列、異なるクラス同士、クラスと int など）は、無言で false にならず位置つきエラーにする。線引きは次のとおり — 型不明（unknown）が絡む場合は従来どおり通す（型の一部に不明を含む場合も同じ）。型変数が絡む場合もジェネリック本体の検査では緩く通し、実体化された時点で具体型同士として判定する（例: メソッド内の `[T] == [int]` は通り、`Box<int>` の実体化で `[int]` と `str` の比較になればその時点でエラーになる）。**bool と int の比較は正当**とする（bool の実体は 0/1 の int 値で、従来から真偽が正しく出ていた）。クラスの `__eq__` / `__ne__` がある場合はその引数の型照合がそのまま異型を弾く。配列同士は要素型の違いを `__eq__` の引数照合で弾く。連鎖比較・安全添え字の比較形の中でも同じ規則が効く（どちらも通常の二項比較の検査を通るため）
- **入口の無いプログラムもリンクできる**: トップレベル文も `def main` も無いプログラム（定義だけのファイルや空ファイル）は、入口シンボルが生成されずリンクエラーになっていた。結合済みのプログラム全体に入口が無ければ空の main（即 0 を返す）を合成する（`ensure_entry_point`、main.c が結合後に1回呼ぶ）。あわせて、入口の有無の判定でメソッド名 `main` を入口と混同しないようにした（従来はメソッド main だけがあるプログラムで合成関数の名前が `__spell_init` になり、やはりリンクできなかった）。仕上げに、suite のプログラム群とドッグフーディングのプログラムを種にしたトークン変形スイープ（1,352件: 削除・複製・置換・隣接交換・切り捨て）を実施し、異常終了・タイムアウトは皆無、リンク失敗はこの入口の件のみ（修正後に再実施して皆無を確認）だった

## 決定: 文字列メソッド第2弾（step 89）

2026-11-28。step 85 の第1弾（starts_with / ends_with / find / contains / split / join / to_int）に続く第2弾を、prelude のみに足した（コンパイラ本体は無変更）。意味論は Python を基準にする。

- **`count(sub)`**: `sub` の重ならない出現回数。**空の `sub` は Python と同じく長さ + 1** を返す（`""` に対しては 1）
- **`strip()`**: 前後の空白を取り除いた新しい文字列。空白の定義は `to_int` と同じコード集合（スペース 32 と 9〜13 = タブ・改行・VT・FF・CR）

## 決定: 同名再定義の禁止とオーバーロード（step 91）

2026-11-28 本人決定「同名再定義はエラーにして。ただしオーバーロードは出来るようにして」。設計相談に gpt-6.2-sol を使用した。

- **再定義エラー**: 同じ名前＋同じ引数シグネチャ（引数の個数と型。戻り値型は含まない）の関数・メソッドの再定義は位置つきコンパイルエラー（2件目の定義位置に、1件目の定義行を示す。1件目が prelude 内の場合は行を示さない）。prelude の関数を同じ署名で再定義することもエラー。**クラス名の再定義も位置つきエラー**（クラスにオーバーロードはない）。あわせて、ジェネリッククラスでは「型引数を当てはめると同じ署名になるメソッドの組」（例: `store(v: T)` と `store(v: int)` を持つ `Box<T>` の `Box<int>`）は実体化の時点で位置つきエラーにする（テンプレート自体は合法で、`Box<str>` のように衝突しない実体化は問題なく使える）
- **解決規則**: 候補は同じ所属（素の関数同士、または同じクラス内）の同名定義。まず引数の個数で絞り、次に各引数を採点する — 全引数が「型不明を含まず厳密に一致」すれば完全一致、全引数が「型不明を同一視する緩い一致」を満たせば緩い一致、それ以外は不一致。完全一致が1件だけあればそれを選び、複数あれば曖昧エラー。完全一致が無ければ緩い一致が1件だけのときに選び、複数あれば曖昧エラー（位置つき、候補の署名一覧つき）。個数の合う候補があっても全て不一致なら「合うオーバーロードがありません」と候補を示す。**bool と int は別型**として区別する。候補が1件だけの名前は従来どおりの解決・診断をそのまま使う（既存のエラーメッセージを変えない）
- **ラベル**: オーバーロードグループ（同名の定義が複数ある所属）の関数は全員、ラベルに署名の接尾辞 `$<引数の個数>$<型>$<型>…` を付ける（例: `spell_f_f$1$int`、`Pair$int$str.m$1$int`）。個数を先に置くことで型ラベルの連結の曖昧さを避ける。関数型の表記にも引数の個数を含める（`fn$<個数>$…`）。これが無いと `fn() -> fn(int) -> str` と `fn(fn() -> int) -> str` のような別の型が同じ表記に潰れてラベルが衝突する（Luna レビューで発見し、再現テストつきで修正）グループでない関数のラベルは従来どおり（生成コードの無用な差分を避ける）。入口（引数なしの `main` / `__spell_init`）は同名の別署名があっても裸の名前のまま。呼び出し・関数参照・定義のすべてが型検査で解決済みの関数を指してラベルを出すため、解決と生成がずれることはない。ついでに、ユーザーが定義した `getchar` / `putchar` に外部シンボル向けの32ビット切り詰め（movsxd）が掛かっていた問題も直した（バグハントの既知件）
- **関数値**: 期待される fn 型（注釈・引数の型など）が分かれば、引数と戻り値の型が合う候補を選ぶ。期待型が無く候補が複数ある場合は位置つきエラー（型注釈でシグネチャを指定するよう案内）。ただしオーバーロードされた関数の直接の引数として渡された場合は解決を保留し、呼び出し先が確定した時点でその引数の型で選び直す（例: `apply(f, 1)` と `apply(f, "a")` がどちらも書ける）
- **組み込みとの関係**: `print` / `eprint` / `exit` の特殊処理は従来どおり「同名のユーザー定義があればそちらが優先」。プロトコルメソッド（`__bool__` やイテレータ・プロトコルなど固定署名で引かれるもの）は、誤った署名のオーバーロードに隠れないよう個数の合う候補を優先して引く。dunder（`__add__` など）も通常のオーバーロード解決を通る
- **prelude の全数確認**: 新しい検査で prelude 自身に違反は無かった。ただしテストスイート test_stmt.sp に同一ヘルパ（`mark` / `check`）の重複定義があり、新規則でエラーになったため重複側を削除した（同一内容の複製で、従来は先勝ちで片方が死んでいた）
- **制限**: オーバーロードされた関数の直接の引数でない位置（ネストした式の中など）にある関数参照は保留の対象外で、曖昧ならエラーになる。ラムダ引数は、候補全員の引数型が一致する位置でのみ型を借りられる（候補で型が割れる位置のラムダは自身の注釈が要る）

## 決定: 論理演算子の英字形 `and` / `or` / `not`（step 94）

2026-11-28 本人決定「andとorも実装して。&&と||と全く同じ」＋追加指示「not も」。

- **`and` は `&&` と、`or` は `||` と完全に同じ**: 同じ短絡評価、同じ優先順位（`and` が `or` より強く結び、`&&` / `||` との混在も自由）。パーサが同じ OP_AND / OP_OR を作るため、typecheck の `__bool__` 変換を含め以降の扱いは記号形と同一
- **`not` は `!` の英字形で、優先順位も `!` と完全に同じ**: 単項の前置演算子として強く結ぶ。Python の `not`（比較より弱く結ぶ）とは違うので、`not a == b` は `(!a) == b` になる。`!;`（break の省略形）は文頭の記号専用の糖衣として残し、`not` には付けない
- **キーワード化**: `and` / `or` / `not` はキーワードになり、識別子としては使えなくなった。prelude と suite に同名の識別子は無かった（全数確認済み）。キーワード表（tokenize.c の2配列）と Keyword enum への追加は末尾に置き、位置対応を維持した
## 決定: スカラーの min / max（可変引数）と abs（step 92）

2026-11-28 本人決定「スカラーの min, max は可変引数でお願い。abs(x) の実装は確定」。

- **min / max は型検査で扱う組み込み**: spell には可変引数の構文が無いため、print / exit と同じく check_funcall の特殊形にした（一般の可変引数構文は作らない）。同名のユーザー定義関数・クラスがあればそちらが優先される（print と同じ方針）。引数は1個以上で、0個は位置つきコンパイルエラー。1個ならその値自体
- **書き換え先は配列リテラルのメソッド**: 2個以上は `[引数...].min()` / `.max()` へ書き換える。意味論は配列メソッドと正確に一致する — `__lt__` で順序が決まる型（int、辞書式の str、成分辞書式の Pos2 / Pos3 など）に使え、引数の型が揃わなければ配列リテラルの要素型検査が位置つきエラーにし、型不明が絡めば緩く通る。配列リテラルは要素を左から右へちょうど1回ずつ評価する（step 87 のヒープ化済み）ため、「各引数は1回だけ・左から右へ」の要件もそのまま満たされる。一時置き場を使う独自の畳み込みは作らなかった
- **引数の上限は設けない**: 通常の関数呼び出しの6個上限は ABI のレジスタ渡しに由来し、リテラル経由のこの形には当てはまらない（配列リテラル自体に個数の上限が無い）。7個以上でもそのまま書ける
- **abs は prelude の通常の関数**（int 用）。最も小さい int（-9223372036854775808）の絶対値は int の範囲に収まらないため未定義（オーバーフローする）。クラス型への `__abs__` 対応は見送った — prelude の通常の関数からは dunder へ振り分けられず、対応するには print のような型検査の組み込み化が要るため（必要になったら別途判断する）
## 決定: f-string（step 93）

2026-11-28 本人決定「f-stringも欲しい」。

- **形**: `f"..."` と `f'...'`（通常の文字列と同じく両方の引用符）。リテラル内の `{式}` が、式の値を文字列化したもので置き換わる。文字列化は print と同じ変換（`__str__` 経由）で、`__str__` の無い型の値と型の分からない値は print と同じくコンパイルエラー。波括弧のリテラルは `{{` が `{`、`}}` が `}`（Python と同じ）
- **脱糖衣**: 字句解析でリテラル全体を1トークン（TK_FSTR。str はソース内の `f` の位置、len は全体の長さ）にし、パーサがリテラル部と式部に分割する。リテラル部は通常の文字列リテラルと全く同じノードにし、式部は対応する `}` の位置に一時的に `\0` を置いてその場で再トークン化し、通常の式として読む（トークンが実ソースを指すため、式の中のエラー位置が正確になる）。この間だけ文単位のエラー回復を切り、式部のエラーを字句解析エラーと同じ「チェック全体の打ち切り」にする（longjmp で復元処理が飛ばされても検査自体が終わるため、大域状態の不整合は残らない）。typecheck が各式部品を `__str__` 変換で包み、str の `+`（`__add__`）の連鎖へ書き換える。新しい実行時機構は無い。補間が1つも無い f-string は、通常の文字列リテラルと全く同じノードになる
- **v1 の制限**: 書式指定（`{x:03d}` の `:` 以降）は未対応。式として読めた後に残る `:` を検出して位置つきエラーにする（スライス `a[1:2]` や括弧内の型注釈の `:` は式の内側で消費されるため誤検出しない。検出方式は実装計画レビューで Luna が提案した「深さ走査ではなくパース後の残りトークンを見る」形を採用）。式の中の `{`（ラムダ本体などのブロック）は未対応で位置つきエラー。式の中のコメントも未対応（式部の終端判定と衝突し、黙って式が欠ける形になるため、文字列の外にあれば明示的にエラーにする）。式の中に文字列リテラルや入れ子の f-string を書くことはできる。型注釈つき代入も式部ではエラーにする
- **構造エラー**: `{` の閉じ忘れ、空の `{}`、対応しない `}`、未終了は全て位置つきエラー（構造検査は字句解析の段階で行う）。式部の後に余分なトークンが残る場合も位置つきエラー

## 決定: 配列の値セマンティクス（step 96）

2026-11-28 本人決定「[[-1]*w]*h と書いたら -1 が全部独立になってほしい」「a = [1,2,3]; b = a としたらディープコピーにしてね」「ぜーんぶディープコピーでよろ」＋原則「spell の原則として使いまわしやポインタなどの面倒な概念は基本ない」「競プロで出てこないから」。

- **原則: 配列は値。束縛ではディープコピーされ、使いまわし（エイリアス）の概念は基本として持たない**。対象は配列のみで、クラスインスタンスは従来どおり参照のまま（str / Pos2 / Dict なども含む）。コピーの深さは静的な型の配列の入れ子の深さから決める。基盤は step 82 の `__rt_spell_copy_array`
- **コピーされる束縛地点**: ローカル／グローバルへの代入（初回束縛を含む）と多重代入の最終束縛、関数引数（配列型パラメータ。コピーは呼び出された側のプロローグで行う）と戻り値、配列リテラルの要素、append の引数、添え字代入・フィールド代入の右辺、Dict への格納値（読み出しは束縛側のコピーで独立する）、for の要素束縛（イテレータ内部の受け渡しと `__next__` の戻り値コピーで実現）、クロージャのキャプチャ（従来の値コピーに加えて配列はディープにする）
- **繰り返しの統一**: `[fill; n]` は fill が配列型なら、リテラルかどうかによらず各スロットが独立（step 82 ではリテラル形だけだった）。配列の `*`（`__mul__`）も、各繰り返し要素が元の配列・他の要素とストレージを共有しない（内部の添え字代入の右辺コピーで自然に実現）。要素が int の繰り返しは従来どおり。str の `*` は従来どおり（中身の [int] は元から独立）。この変更で step 82 の「非リテラル fill は共有」（旧 t106）と step 65 の「容量内 append が別名から見える」意味論は廃止された
- **コピーしないもの**: メソッドのレシーバ `self` は借用（sort / append / Deque の push のように変数そのものを書き換えるため）。`a[i][j] = x` のような左辺値の連鎖の中間もコピーしない（コピーされるのは右辺の値だけ）。型不明の値は深さが決められないのでコピーできない（現状維持）。この非対称性のため、`d[k][j] = v`（Dict の値への連鎖代入）は `__getitem__` の複製への書き込みになり辞書へ届かない — `tmp = d[k]; tmp[j] = v; d[k] = tmp` と書く
- **反復への影響**: ArrayIter は受け取った配列のスナップショットを回る。ループ中の元配列への append は反復に増えず、step 58 のループ変数の書き戻しもスナップショットにだけ効いて元の配列へは届かない（str の反復では従来どおり届く）。書き戻しを固定していたテスト（test_stmt の t072〜t075）は新意味論に合わせて期待値を変更した
- **実装**: 型検査が束縛地点で ND_COPY ノードを挿入し、コード生成が `__rt_spell_copy_array` 呼び出しに下げる。作られたばかりの値（リテラル・`[fill; n]`・呼び出し結果・ND_COPY 自身）はコピーしない（freshness 省略）。素のローカル変数をそのまま返す場合もコピーしない — このコピー規律のもとではローカルの配列は常にその呼び出しが独占しているので、フレームが消える return では所有を移して安全（prelude の `__add__` / `sorted` などの無駄な複製を避ける）。複合代入の内部の一時代入は「場所の借用」としてコピーを止める印（`no_bind_copy`）を付けた
- **性能への配慮**: prelude 側のホットパスは、束縛コピーが全体複製にならない形に直した（str の `__init__` は要素の移し替えをやめて代入のみに、Dict のテーブル成長はフィールドの配列を append で直接伸ばす形に、Vec の append も同様）。ベンチ（spell-bench、同セッション交互測定・最小値比）: array_fill_sum 1.00、sieve 1.03、grid_dp 0.98、dict_ops 0.96、sort_sum 1.01、str_build 0.76（改善）。method_calls は 1.06 だがホットパスのアセンブリは変更前と同一で、配置ずれの範囲

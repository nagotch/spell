# Spell 言語設計メモ

2026-11-21 の設計議論の記録。実装仕様ではなく、決定事項と未決定事項の整理である。
元の設計の正本は spell_v0 の `DESIGN.md`、`docs/reference.html`、`docs/design-review.md` とし、
本メモは主にそれとの差分と、新しい spell での新規決定を記録する。

なお、この `docs/` は将来 GitHub Pages でドキュメントを公開する土台にする想定である。

## 目標

- 競技プログラミングで便利で、速く書けて、デバッグしやすい言語にする
- 優先順位は spell_v0 を踏襲する: 実行速度 > 打鍵数の少なさ > 競プロ頻出処理の支援 > 楽しさ > 一貫性 > 読みやすさ > 汎用性
- ただし読みやすさは「初見で理解できるか」ではなく「慣れた利用者が速く正確に読めるか」で測る

## 基本原則

1. **コアは小さく地味に保ち、spell らしさは糖衣構文で作る**
   - コアは変数・関数・分岐・ループ・配列・基本入出力だけの平凡な言語にする
   - spell らしい短縮や記号は、すべてコアへ展開できる糖衣として置く
2. **記号糖衣の採否は、初見の読みやすさでは決めない**
   - 判定条件は「頻出であること」「1記号1意味で、一意に展開できること」「糖衣の語彙総量を小さく保てること」
   - 頻度が低い記号は慣れが効かないため、原則として採用しない
3. **記号糖衣は、必ずアルファベット形の正規表記を持つ**
   - 展開コマンドは、記号形からアルファベット形への書き直しまでを行う（コアへの完全展開はしない）
   - 展開結果も、そのまま実行できる spell でなければならない（デバッグ時の切り分けに使うため）
4. **糖衣の採用基準は spell_v0 の design-review を継承する**
   - 代表問題で繰り返し現れる
   - コア操作への展開が明確で、実行時コストを増やさない
   - 既存の短縮構文と記号の役割が衝突しない
   - 型エラーと生成コードを利用者が追跡できる
5. **コンパイラは最小限にし、ライブラリ側で充実させる**
   - コンパイラが知るのは汎用の仕組み（変数・関数・クラスとメソッド呼び出し・ダンダーへの展開規則・最小限の intrinsic）だけにする
   - 配列や文字列のような具体的な型の振る舞いも、コンパイラの特殊扱いではなく prelude のクラス定義として置く
   - 機能を足したくなったら、まずライブラリで書けないかを考え、書けない場合だけコンパイラ側の最小の原始機能を足す
6. **基本は Pythonic にする**
   - 意味論や基本構文で判断に迷う点は、Python の意味論を既定とする（反復、トップレベル、除算・剰余など、個別の決定もこの原則に沿う）
   - ただし既決の事項（打鍵数優先の糖衣、優先順位づけ）はこの原則より優先する。Python に寄せるのは未決定の迷いどころだけ

## 決定: for と範囲

- `for` の3形態は spell_v0 を継承する
  1. 整数レンジ（`for i in n:` は 0 から n-1）
  2. 配列・文字列の要素走査（走査変数は要素への可変参照）
  3. 回数リピート（`for n:`、束縛変数なし）
- **短縮形は `@` を spell_v0 のまま採用する**: `i@n:`、`i@0..n:`、`@n:`（変数なしリピート）、`ai@a:`（要素走査）。正規形は `for` を使った形で、展開コマンドでそちらへ書き直せる
  - 併せて、break の省略形 `!` と continue の省略形 `^` も spell_v0 のまま採用する
  - 検討して却下した代替案: `i~n:`（`i..n` と見間違える）、`for` を落とす形（分かりにくい）、`i::n:`、`i$n:`、`for i..n:` の融合形。最終的に `@` へ戻した
- 右辺の式は最初に1回だけ評価する。本体で式に使われた変数を書き換えても反復回数は変わらない
- 回数が0や負数のときは0回で、何もしない
- ループ変数はフラットスコープの普通の変数として残る。終了後の値は範囲の外側の値とする
- 範囲は spell_v0 を継承する: `a..b` は半開区間 [a, b)、`a..=b` は終端を含む [a, b]
- **`.rev` を基本操作として新設する**（spell_v0 には存在しない）。範囲・配列・文字列の並びを逆順にする
- **逆範囲は糖衣とする**
  - `a..b`（a > b のとき）は `(b..a).rev` の省略形
  - `a..=b`（a > b のとき）は `(b..=a).rev` の省略形
  - 端点の扱いは「集合は昇順と同じで、順序だけが逆」。例: `n..0` は n-1, n-2, ..., 0
  - 変数が端点で実行時に大小が決まる場合も、意味は「始点の側から終点へ向かう並び」で一貫させる
  - 展開コマンドでの正規形は `(0..n).rev` の形である
- ライブラリ関数の契約は spell_v0 を継承する。`bisect` は昇順範囲を受ける。`a.sum(l..r)` は 0 <= l <= r を前提とする

## 決定: 入出力

spell_v0 で確定済みのものは継承する。

- 入力: `x = in`、`s = in_str`、`a, b = in`、`a = in[n]`、`a- = in[n]`、`words = in_str[n]`、既存要素への `>> a[i]`。`in` は代入の右辺全体でのみ使用できる
- 短縮形: 入力 `>> x`、出力 `<< x`
- **`>> a, b, c` の複数対象（step 62）**: 対象をカンマで並べると、各対象へ `in` を左から順に代入する並び（`a = in; b = in;`）へ展開する。対象の形は単独形と同じ（識別子・添字・メンバー）。`in[n]` などの他形式は対象ごとに書けない
- 出力: `put` は配列を空白区切りで1行に、二次元配列は行ごとに改行して出す。Bool は 1 / 0
- `yn` による Yes / No 出力、stderr への出力は `eprint`（step 59 で `cerr` を統合。後述）

新規の決定:

- **行入力を追加する**: `s = in_line` を `in_str` と並ぶ形で置き、空白を含む行を読めるようにする（spell_v0 はトークン読みのみで、design-review でも弱点とされていた）
- **二次元入力は `a = in[h][w]` と書く**: `in[w]` を h 回読む合成として定義し、結果は二次元配列（Array<Array<Int>>）になる。`a[y][x]` でアクセスでき、`put` の二次元配列の行ごと出力や `for row in a` とそのまま噛み合う。辺リストは `a = in[n][2]` と書く
  - 一次元で読みたい場合は、従来通り `a = in[h * w]` も書ける（個数が任意の式でよい、という `in[n]` の一般性はそのまま残る）
  - 文字グリッドは従来通り `in_str[h]` で行ごとの文字列として読む
- **入力の過不足は、手元の実行では静かに通さない**: 読みすぎたら即エラーにする。終了時に読み残しがあったら警告する（読み個数のずれを早期に見つけるため。提出モードでの扱いはデバッグ設計と一緒に決める）
- **`put x, y` の複数値出力を正式に認める**: 空白区切りで並べて、末尾に改行を付ける

## 決定: デバッグ設計

spell_v0 の現状は、`--submit` で `cerr` を除去できるだけで、境界チェックなどの切り替えは未実装だった（DESIGN.md の構想のみ）。新しい spell では次で確定する。

- **モードの原則**: 同じソースから Debug（手元の実行）と Submit（提出用）の2つのビルドを作る。検査は正しいプログラムの意味を変えず、壊れた状態を静かに通すか、その場で止めるかだけを変える
- **エラー表示**: spell の言葉で、発生した行と関係した値を含めて出す（例: 添字の値と配列の長さ）
- **Debug で検査するもの**:
  - 配列の境界外アクセス（読み書き両方）。安全添字 `a?[i]` は「範囲外かもしれない」の意思表示として対象外にし、spell_v0 の意味（条件式・比較式では false）を変えない
  - 整数オーバーフロー、0除算
  - 入力の読みすぎ（即エラー）と読み残し（警告）
  - 空配列への `a.min` / `a.max` のようなライブラリの契約違反
- **Submit での扱い**: 境界外アクセスは未定義（速度優先）。ただし整数オーバーフローは「2の補数で巻き戻る」と定義し、挙動の決定性は残す
- **`cerr`**: spell_v0 を継承し、提出モードで除去される。引数が変数や添字式のときは `x = 3` のように名前つきで出す（step 59 で、stderr への出力そのものは `eprint` として先行実装した。独立した `cerr` 構文は入れず、提出モードで除去する対象は将来 `eprint` とする）
- **`assert`**: 置く。Debug では失敗した行と式を出して止まる。**Submit では除去する**。そのため、assert の条件式に副作用を書くとモード間で挙動が変わるので、条件は副作用なしを規約とする

## 決定: エラー出力

- エラーは4分類し、出し方を分ける: (1) 字句・構文エラー（コンパイル時、位置つき） (2) 意味エラー（コンパイル時、位置つき。未定義変数の読み取りなど） (3) 実行時エラー（Debug 検査が止めるもの。位置＋関係した値つき） (4) 内部エラー（コンパイラのバグ。「プログラムではなくコンパイラ側の問題」と明示し、内部情報を出してよいのはこの分類だけ）
- 文面は日本語で、spell の言葉で書く（レジスタ名や実装言語の都合は出さない）。「期待したもの」と「実際のもの」を両方出す
- 最初のエラーで即終了する（エラー回収はしない）。警告（読み残した入力など）は同じ形式で、終了しない
- 表示形式: 先頭に `ファイル名:行:列: エラー: 文面`、続けて行番号つきでその行を表示し、問題のトークンの範囲いっぱいに `^` の下線を引く（1点のキャレットではない）
- 実行時エラーも同じフル表示にする。そのため Debug ビルドでは、検査のある行の本文をバイナリへ埋め込む（埋め込みは Debug のみ、対象は検査のある行だけ）
- 未定義変数のエラーでは typo の候補提示を行う: 編集距離の近い既存変数があれば「もしかして `名前` ですか（定義は N 行目）」と添える。対象は未定義変数のエラーに限る
- 細部: 色付けは標準エラーが端末のときだけ（パイプ時はプレーン）。下線の範囲が複数行に及ぶ場合は、表示している行の範囲内だけを引く

### エラー出力の追加決定（Sol レビューを経て）

- 分類に **ドライバエラー** を加える（計5分類）: ソースファイルが開けない、外部アセンブラ／リンカの起動失敗など、ソース位置を持たない失敗。内部エラーとは分ける。実行時エラーのフル表示が約束できるのは spell の検査が検出した失敗だけで、OS に強制終了された場合まで約束しない
- 指す対象は「トークン全体」固定ではなく **主位置**（原因を説明する範囲、または挿入点）とする: `)` の欠落のような場合はゼロ幅の挿入点に `^` を1つ置く。実行時エラーでは式全体ではなく原因の部分（`a[i]` なら `i`、`x / y` なら `y`）を指す
- 関連する別の場所は2件目のエラーにせず **補足位置** として示す（対応する開き括弧の位置、定義位置など）。文面でも事実は `補足:`、推測は `ヒント:` と書き出しを分ける（typo 候補は `ヒント:`）
- 位置の内部表現はバイト範囲 `[start, end)`、行・列は1始まり。列番号は Unicode コードポイント単位で数え、下線は表示幅で合わせる。タブは表示時に展開する（日本語コメント等の全角文字で下線がずれないようにするため）
- 位置がないエラーでは見出しの位置を省く（`0:0` のような架空の位置は出さない）
- 入力エラーは理由を分ける（入力の終わりに達した／形式が違う／値が範囲外）。読み残し警告は、既に読み込んだバッファ内に非空白の残りがある場合だけ出す（追加の読み取りで端末やパイプを待ち続けないため。警告がないことは読み残しなしの保証にはならない）
- typo 候補の出し方: エラー地点から参照できる変数だけを対象にし、短い名前ほど厳しく判定する。同率・僅差なら出さない。最大1件
- Debug 検査は危険な演算より前に行い、オペランドを二重評価しない（符号付き最小値を -1 で割る場合もゼロ除算と並ぶ検査対象）
- `assert` と `cerr` は Submit で引数ごと評価しない、を仕様として明記する（既存の「副作用を持たせない」注意の格上げ）。除去されるコードも両モードで意味検査は行う

## 決定: フルクラスとダンダーメソッド規約

- **フルクラスを新設する**（spell_v0 にはクラスもユーザー定義型もなかった）。自作データ構造（セグメント木、Union-Find など）を spell のライブラリとして書けることが、競プロ用途での大きな利点になる
- 動機のもう半分は、コンパイラからライブラリ都合の特殊扱いを消すこと。現在の `.len` は、パーサが特別扱いし、コード生成が「要素の手前に長さを置く」という配列の表現を直接知っている。これをやめる
- 演算子・添字・長さ・反復は **ダンダーメソッド規約への展開** とする: `a[i]` → `__getitem__`、`a[i] = x` → `__setitem__`、長さ → `__len__`、`for x in a` → 反復の規約、など。コンパイラが持つのはフィールドアクセスとメソッド呼び出しの一般機構と、この展開規則だけ
- 配列や文字列も prelude でクラスとして定義する。コンパイラに残る原始機能は、連続領域の確保など最小限に痩せさせる
- **継承はなし**: ダンダー規約は「その名前のメソッドがあるか」だけで成立するので継承は不要。共有は委譲で足りる。型推論とメソッド解決を軽く保つ
- **`self` は Python 式に明示する**: メソッドの最初の引数として書き、中では `self.data` と書く。裸の名前はローカル変数、`self.` つきはフィールド、と区別を固定する（代入で変数が生まれる言語なので、この区別が曖昧だと事故になる）
- **クラスまわりの構文は可読性優先**: クラスはコンテスト中に書くものではなく、事前にライブラリとして書いておくものなので、打鍵数より可読性を優先する（コンテスト中のコードに適用する速さの基準とは使い分ける）
- **フィールドはクラス本体で宣言する**: フィールドの一覧が一目で分かり、レイアウトが宣言で固定される（静的型＋推論との相性もよい）。`__init__` の代入で生やす Python 式は採らない
- **ダンダーとコンストラクタは Python 式の `__名前__` で統一する**: コンストラクタは `__init__(self, ...)`、長さは `__len__`、添字は `__getitem__` / `__setitem__` など。アンダースコア2つが「規約専用の別枠」の目印になり、通常のメソッド名と衝突しない
- クラス構文の字面: `class SegTree:` / 型パラメータつきは `class SegTree<T>:`。メソッドはクラス内でも `def` を使い、`self` に注釈は付けない（所属クラスから決まる）
- フィールド宣言は `data: Array<T>` の形で、**型が必須**（これは任意注釈ではなくフィールドそのものの宣言）。`self.x = ...` は宣言済みフィールドへの代入に限り、未宣言名への代入はエラー
- フィールドの初期値はクラス本体に書かず、`__init__` での代入に集約する。コンパイラは「正常終了する全経路で全フィールドが初期化されること」と「初期化前の読み取りがないこと」を検査する
- 型パラメータは定義側で明示し、生成時は `SegTree(...)` と書いて、コンストラクタ引数と束縛先の注釈の両方から推論する。どちらからも決まらなければ、注釈を求めるエラーにする。`<...>` は初版では型を書く位置にだけ置く
- コンパイラ組み込み（intrinsic）は v0 と同じ `__spell_` 接頭辞の名前で、prelude のクラスメソッドの本体に閉じ込める
- **0引数メソッドは `()` を省略できる**（ドットの後に限る）: `a.len` は、フィールドなら読み出し、`self` 以外の引数を持たないメソッドならその呼び出しとして解決する。同名のフィールドとメソッドの共存は禁止し、静的に一意に決める
- これにより **`len` は Array 等の普通のメソッドとし、`__len__` は設けない**。ダンダーは構文が起点になる操作（添字・演算子・反復など）に限る。既定の `.rev` もこの規則で説明できる
- メソッドを関数値として欲しい場合はラムダで包む（`a.m` の意味が期待型で変わる規則は採らない）。メソッドを値として渡す書き方はそもそも可読性が下がり、コンテスト中にはやらないので、ラムダで十分という判断。トップレベルの関数には省略を広げない（`f` は関数値、`f()` が呼び出し）
- メソッドへの代入（`a.len = 3` 等）はエラーとする（暗黙の setter は作らない）。関数型フィールドの `a.m()` は、フィールドの関数値を呼び出すものとして区別される
- ライブラリのスタイル: 括弧なしで書けるメソッドは、計算量と破壊的かどうかを API 側で明記する（フィールド読み出しに見えるため）

## 決定: 型注釈は任意（クラスでは明示が推奨スタイル）

- **型注釈は書いても書かなくてもよい**とする。spell_v0 の「型注釈を一切なくし、すべて推論する」方針からの変更。書いた注釈は推論結果と照合される制約になり、書かなければ推論される
- **クラス（=事前に書くライブラリ）では型を明示して書くのを推奨スタイルとする**: フィールドとメソッドのシグネチャに型を付け、契約を固定する。可読性優先の原則の適用で、v0 の「シグネチャは最初の呼び出し箇所から遅延推論する」方式の不安定さ（ライブラリ側の契約が利用側で決まってしまう）への対策にもなる
- コンテスト中に書くコードでは省略して速さを取る。型パラメータもこの枠組みで扱う（クラス定義側で明示し、利用側では推論）
- 型注釈の字面は v0 の prelude と同じ: 引数・束縛は `名前: 型`、戻り値は `-> 型`、型引数は `Array<Int>` の形
- 注釈を書ける場所: フィールド（必須、上記）、引数（任意）、戻り値（任意）、ローカル変数の初回束縛 `x: Int = 式`（任意）。再代入への注釈と、初期値なしのローカル宣言は初版では入れない
- 注釈はキャストではなく型制約で、推論の事後照合だけでなく、注釈側から右辺・生成式の推論へも制約を渡す（双方向）

## 決定: 実装言語は C で継続する（Rust 移行は取りやめ）

- 2026-11-23 午前、一度は spell 化フェーズの実装言語を Rust とする決定をしたが、同日、再判断で取りやめた。理由: 既に C で実装が進んでいる以上、移植コストのほうが利得より大きい
- C 版が本線のまま続く。残課題は本のステップ（コメント、グローバル変数）、`%`、`&&` / `||` / `!`、その先の spell 化フェーズ（字下げ構文・型推論など）
- 本書の言語設計の決定（最小コア＋prelude、脱糖フェーズ、クラスとダンダー、エラー出力など）は実装言語に依存しない設計として有効なまま。脱糖規則の実装は C の構文木書き換えとして行う（仕様は項書き換えの記法で記述し、実装と対応させる方針は変わらない）

## 決定: 除算と剰余

- **除算は床除算、剰余は除数と同じ符号（Python 式）**: `-7 / 2` は `-4`、`-7 % 2` は `1`。`a == (a / b) * b + a % b` が常に成り立ち、正の除数では剰余は常に非負になる
- 現在の C 実装はハードウェアの切り捨てのままで、この決定に合わせて補正する作業が残る

## 決定: トップレベルとグローバル変数

- **トップレベルには文・関数定義・クラス定義を混ぜて書ける**（v0 / Python 式）。文は上から順に実行され、`main` 関数の入れ物は不要
- トップレベルでの代入がグローバル変数の作成になり、関数の中から読み書きできる。これがグローバル変数の表面構文を兼ねる

## 決定: 脱糖フェーズと for の while 化

- **コンパイラ前段に脱糖（lowering）フェーズを設ける**: 構文解析後の構文木を歩き、糖衣のノードをコアのノードの組み合わせに置き換える。`for` 単独ではなく、複数の構文を共通基盤でまとめて下ろすことで意味を持つ
- 脱糖で下ろす対象: `for`（範囲・要素・回数）→ `while` と反復プロトコル、`for...else` → 終了フラグつき `while`、`elif` → 入れ子の `if`、`!` / `^` → `break` / `continue`、複数代入・分割代入 → 一時変数への退避＋個別代入、比較の連鎖 → 一時変数＋短絡、複合代入・増減・`<?=` → 読み出し・演算・書き戻し（左辺の評価は1回だけ）、`a..b` → Range の生成、`.rev` と0引数メソッドの括弧省略 → 通常のメソッド呼び出し、添字・演算子 → ダンダー呼び出し、入出力構文 → ライブラリ呼び出し
- 下ろした後に残る最小コア: リテラル、変数、関数・メソッド呼び出し、基本演算、単一代入、ブロック、`if`、`while`、`break`、`continue`、`return`、関数定義、クラスの実行時モデル
- 共有基盤: 隠しシンボルの発行（ソースから参照できない内部シンボル。フラットスコープに漏らさない）、生成ノードへの元のソース位置のコピー、評価順序を守るため一時変数化、ループ文脈の管理（どの `break` / `continue` がどのループ宛か）
- `for` の展開の要所: 範囲の端点は1回だけ評価して隠し変数へ。その `for` 宛の `continue` はステップ処理（カウンタ加算）を通る形に書き換える
- **ループ変数は内部カウンタとは別（Python 式）**: 本文でループ変数を書き換えても反復には影響しない。ループ後のループ変数は最後に反復した値を保持し、範囲が空なら代入自体が起きない（従前の状態のまま）。旧決定「範囲外の値で終わる」はこの決定で置き換える
- **`for ... else` は継承する**: break しなかったときだけ else 側を実行する（Python と同じ）。脱糖では終了フラグで実現する
- **要素反復はイテレータプロトコルに統一（Python 式）**: `for x in obj` は `obj.__iter__()` の返すイテレータから値を取り出す形に展開する。配列・範囲もイテレータを返す。範囲反復の内部カウンタもイテレータ側が持つため、「ループ変数を書き換えても反復に影響しない」とも一貫する
- **ループ変数への代入は要素へ書き戻す（step 58、旧決定「代入しても書き戻らない」を変更）**: イテレータが任意メソッド `__set_current__(v)` を持つ場合、本体でのループ変数への代入は各反復の終わり（と、このループ宛の `break` / `continue` の直前）に書き戻される。配列（`ArrayIter`）と文字列（`StrIter`）が持つ。持たない反復（範囲・Dict のキーなど）でのループ変数への代入は、書き戻されずに消える事故を防ぐためコンパイルエラーにする。`return` で抜ける場合は書き戻さない。あわせて、文字列の反復は1文字ずつの `str` を返すよう変更（添字 `s[i]` は従来どおり `int` の文字コードを返す）
- `assert` / `cerr` の Submit 除去は脱糖に混ぜず、ビルドモードの処理として分ける
- 脱糖の実装は当面、規則ごとの手書き方式で続ける。規則をデータとして持ち汎用エンジンで適用する「規則エンジン方式」（仕様の記法がそのまま実装になる形）は、規則の数が増えたら再検討する（保留）
- **糖衣規則の表現は項書き換えの記法で書く**: 正規表現（文字列置換）では入れ子・評価順序・文脈を扱えないため採らない。仕様ではメタ変数（式・文・名前などの構文カテゴリ）を使った書き換え規則として記述し、実装は構文木のパターンマッチで規則と1対1に対応させる。テストは規則ごとに「入力 → 展開後」の対応で置く

## 速く書ける構文の候補（頻度順）

ほぼ全ての問題で使う層:

- 入力: `n = in`、`a, b = in`、`a = in[n]`、`a- = in[n]`（入力修飾子 `-` の正規形は `-= 1` への展開）
- 出力: `put x`、`put x, y`、`put a`（配列を空白区切りで出す形は採用方向）
- ループ: 上記の `for`
- 更新: 複合代入、`ans++`（正規形は `ans += 1`）、`a, b = b, a` の交換

頻出層:

- 連鎖比較 `a < b > c`（正規形は `and` で繋いだ形）
- 配列メソッド: `a.sum`、`a.len`、`a.min`、`a.max`、`a.sort`、`a.rev`、区間和、二分探索
- スライスと範囲: `a[1..]` など

## 決定: 辞書

- **辞書型を入れる**（v0 には無かった型を新設）。prelude のクラスとして実装し、コンパイラは汎用の仕組みだけを持つ（最小コアの原則どおり）
- **未存在キーは初期値で生やす**（defaultdict 式）: `cnt[x]++` のような数え上げがそのまま書けることを優先する。初期値の具体的な定義（型ごとの既定値をどこまで用意するか）は別途決める

## 決定: `<?=`（chmin / chmax）は入れない

- `x <?= y` の糖衣は採用しない。緩和は `x = min(x, y)` と書くか、更新の有無が要る場面では `if` を直接書く
- 判断の根拠: 関数風の正規形 `chmin(x, y)` は呼び出し元の変数を書き換える特殊形になり、コンパイラに専用の知識を持たせることになる。**できるだけコンパイラに頼らない**（汎用の仕組みとライブラリで済ませる）という方針を優先した

## 決定: セルフホスト向けプリミティブと Vec（step 59）

セルフホスト（コンパイラを spell 自身で書く）に向けた前提として、ドライバ層の機能を入れた。

- **公開 API は prelude の通常の関数・クラス**: `args() -> [str]`（`[0]` はプログラム名、C / sys.argv と同じ）、`read_file(path) -> FileData`、`write_file(path, text) -> bool`、`exit(code)`、`eprint(x)`（print の stderr 版）
- **失敗は `FileData { ok: bool, text: str }` で表す**: null も例外も入れない既定どおり。開けない・読み切れないとき `ok = false`、空のファイルは `ok = true` で `text = ""`
- **中身はコンパイラ組み込みプリミティブ `__spell_*`**: `[int]` の文字コード配列と `int` だけを扱い（`__spell_argc` / `__spell_argv_chars` / `__spell_read_file_chars` / `__spell_io_ok` / `__spell_write_file_chars` / `__spell_stderr_chars` / `__spell_exit`）、型検査に署名表を持ち、誤用は型つき・位置つきエラーにする。codegen は呼び出しをランタイムヘルパ（`__rt_spell_*`、libc のみ使用）への呼び出しとして出す。ヘルパの出力は step 63 以降、到達可能なプリミティブ呼び出しがあるものだけに限る
- **`exit` は prelude 関数にせず、型検査でプリミティブ呼び出しへ書き換える**: spell 関数のラベル `exit` が libc の `exit` と衝突し、ヘルパからの呼び出しが自分自身へ戻ってしまうため（print と同じ方式）。ヘルパ側も、利用者が同名関数を定義した場合に備えて libc の `exit` を名前で呼ばず、`fflush(NULL)` で stdio を流してから `_exit` で終わる（生成コードは atexit を登録しないので観測できる挙動は同じ）。stderr へは libc の `stderr` シンボルを参照せず、fd 2 への `write` で出す（NASM 変換でデータシンボルの extern が要らない）
- **`cerr` は `eprint` に統合**: 独立した cerr 構文は入れない。Debug / Submit のビルドモードを実装するときは、除去の対象を `eprint` として再検討する
- **`Vec<T>` を prelude に追加**: 末尾への追加が容量の倍増で均し定数時間になる伸びる配列。生成は Dict と同じく既定値ファクトリを受け取る。添字と `len` は論理長を見て、反復は開始時点のスナップショットに対するもの。なお、テストスイートの自作クラス `Vec`（2次元ベクトル）と名前が衝突したため、テスト側を `Vec2` へ改名した（prelude が名前を取る影響範囲の実例）

## 決定: 生成コードは到達可能な関数だけを含む（step 63）

- **出力は入口（`main` と `__spell_init`）から辿れる関数だけ**: codegen は出力前に AST を辿り、呼び出し・メソッド呼び出し・構築（`__init__`）・関数参照・ラムダの辺を集めて到達可能性を印付けし、印の無い関数はアセンブリへ出さない。prelude の未使用部分（Dict や Vec など）も落ちるため、提出用アセンブリが数千行から実用的な長さになる。ランタイムヘルパ（`__rt_spell_*`）も、到達可能なプリミティブ呼び出しに対応するものだけを出す

## 決定: Deque を prelude に追加（step 64）

- **`Deque<T>` を prelude に追加**: Queue と Stack を兼ねる両端キュー。中身は円環バッファ（先頭位置 `head` と要素数 `n`）で、容量の倍増時に直線化してコピーする。生成は Vec / Dict と同じく既定値ファクトリを受け取る
- **API**: `push_back` / `push_front`（戻り値なし）、`pop_back` / `pop_front`、`front` / `back`（覗き見）、`len`、添字は論理位置（`q[0]` が先頭）、反復は先頭から末尾へのスナップショット
- **空での pop / front / back は誤りで結果は不定**: 配列の範囲外アクセスと同じく検査はしない（境界検査は言語全体の未実装事項）
- **v0 との差**: 破壊的メソッドへの `!` 接尾辞は入れない。`q = deque` のような型推論による生成もせず、期待型＋ファクトリの既定どおりにする（矢印演算子は当初見送ったが、step 66 で dunder プロトコルとして入れた。後述）

## 決定: 配列を append で伸ばせるようにする（step 65）

2026-11-27 に本人が選択肢 A（配列自体を Python の list 風に伸ばせるようにする）を決定。実装方式は「実行速度 > 書き心地」の優先順位に従い、要素アクセスの速さを落とさない形にした。

- **容量ヘッダ方式**: 配列ブロックを `[cap][len][要素...]` に拡張する。要素0の位置と `len` の位置（要素0の8バイト手前）は従来どおりで、cap は16バイト手前。添字アクセスと `.len` の生成命令は変更前とバイト単位で同一（検証済み）。全ての生成経路（リテラル・`[fill; n]`・空リテラル・文字列リテラル・ランタイムヘルパーが作る配列）で cap = len に初期化する
- **`a.append(x)` は prelude メソッドではなく、型検査で組み込みノードへ書き換える**（exit の書き換えと同じ方式）。メソッドでは呼び出し元の変数を付け替えられないため。ユーザークラスが自分で定義した `append` メソッドは従来どおり使える（書き換えは配列型のレシーバだけ）
- **成長は realloc を使わず、malloc＋コピーで付け替える**: realloc はブロックが動くと別名（`b = a`）が宙に浮いたポインタになるため不採用。新しいブロックへコピーし、対象スロットにだけ新しいポインタを書き戻す。古いブロックは解放しない（言語全体の方針）。別名は古いブロックと古い長さを安全に見続ける
- **分裂の意味論**: 容量内（len < cap）の append は共有ヘッダの長さを増やすので別名・引数経由でも見える。容量超過の append は対象スロットだけを付け替えるので、別名と呼び出し側には伝わらない。作りたての配列は cap = len なので、初回の append は必ず付け替えになる
- **戻り値は新しい長さ（int）**: 配列自体は返さない（`a.append(x).append(y)` のような連鎖は、一時値への append がエラーになる仕様と矛盾するため）
- **対象はスロットを持つ場所だけ**: 変数・捕捉変数・フィールド・配列の要素。`(a + b).append(x)` や `f().append(x)` のような一時値は、書き戻す先が無いのでコンパイルエラーにする
- **評価順序**: 対象スロットのアドレスを1回だけ計算 → 値を評価 → スロットから現在のポインタを読み直す。内側 lvalue の規則として、`rows[0].append(f())` で `f()` が `rows` 自体を伸ばしても、外側の書き戻しは捕捉済みの旧スロットへ行く（lvalue は再計算しない）
- **反復中の append**: イテレータは開始時点のポインタを持ち、長さはそのブロックのヘッダを毎回読む。容量内の append は反復にも伸びが見え、成長した append の後はイテレータは旧ブロックの範囲をたどる（テストで固定）。古いブロックは解放されないので、どちらも壊れない

## 決定: 矢印演算子 `<-` / `->` は dunder プロトコルへの書き換え（step 66）

2026-11-27 に本人が「4つとも全て入れる。Deque なら pop/push、両方 int なら比較に、型で解決する」と決定。あわせて「演算子が通常メソッドを呼ぶのは気持ち悪い。dunder にして、通常メソッドは内部で dunder を呼ぶ形に」という設計原則の指摘があり、step 42 の dunder 書き換えの統一規則に揃えた。

- **実体は dunder プロトコル**: `__push_back__(v)` / `__push_front__(v)` / `__pop_back__()` / `__pop_front__()`。演算子は通常メソッドを直接呼ばず、この dunder へ書き換えられる。Deque の公開メソッド `push_back` 等は dunder を呼ぶだけの薄いラッパーにし、公開 API は不変。ユーザークラスが dunder を定義すれば、そのクラスでも矢印が使える（Deque 専用の決め打ちではない）。push 系 dunder の戻り値は self（コンテナ自身）
- **解決順（型検査で型により解決）**: `A <- B` は 1) `A.__push_back__(B)`、2) `A = B.__pop_front__()`（A は代入可能な対象: 識別子＝新規束縛も可・添字・フィールド。代入文の左辺規則と同じ）、3) 両辺が int なら比較 `A < (-B)`。`A -> B` は 1) `B.__push_front__(A)`、2) `B = A.__pop_back__()`、3) 両辺が int なら比較 `A > (-B)`。どれにも当たらなければ位置つきコンパイルエラー。比較形の右辺（符号反転される側）はノードを1回だけ使うので、評価はちょうど1回
- **ラムダとの曖昧性（`->` のみ）**: 裸の識別子 `x -> 式` は、x が現在のスコープで束縛済みなら矢印演算子、未束縛なら従来どおりラムダの引数名として解決する。束縛の有無はパーサの名前表（型検査が使う束縛構造そのもの）で判定する。帰結として、束縛済みの int 変数と同名の引数を持つ裸ラムダは書けなくなる（比較に解決される。ラムダが要れば `fn` 形で書く）。`(x, y) -> 式` と `fn` 形は形で区別できるので無変更。左辺が識別子でない式（`q[0] -> x` 等）は最初から矢印
- **連鎖はエラー**: `a <- b <- c` のように矢印同士をつなぐと、どちらの向きに結合しても意味が曖昧なのでコンパイルエラーにする
- **字句**: `<-` は2文字記号として、隣接している場合だけ結合する。`a < -b` のように空白があれば従来どおり `<` と単項 `-`（なお `a<-b` と詰めて書いても、両辺 int なら比較フォールバックで意味は同じになる）。優先順位は代入に準ずる低さで、右側は完全な式を取る
## 決定: ブロックは `:` ＋インデント形式も使える（step 67）

2026-11-27 に本人が決定（2026-11-25 の「いったん今のまま（`{}` のみ）」という棚上げを覆す）。`{}` は見た目がすっきりしないため、`:` 形式を正規形とし、`{}` も併用可とする。

- **両形式の併用**: ブロックは箇所ごとに独立に選べる。文の頭の直後が `{` なら波括弧ブロック、`:` ならインデントで範囲を決めるブロック（suite）。同じファイル・同じ入れ子の中で混在してよい
- **対象**: `def`、`class`、`if` / `elif` / `else`、`while`、`for`（for...else を含む）、`@` 系の糖衣が取るブロック。ラムダ `fn(...) { }` の本体は `{}` のみ（式の内側にインデントを持ち込まない）
- **suite の形**: `:` の後に改行し、より深くインデントされた文の並びがブロックになる。`:` の同じ行に文を1つ書く1行形も可（`if (x == 0): return 0`、`def f(): return 1`、クラスも `class P: x: int` のように同じ行にメンバを並べられる）
- **空の suite は位置つきコンパイルエラー**（Python と同じ。`{}` の空ブロックは従来どおり可）
- **インデントの数え方**: 行頭の空白を列で数え、空白は1列、タブは次の8の倍数の列まで進める（Python と同じ）。空行とコメントだけの行は判定に使わない。dedent が既存のどの段にも一致しない場合は、位置つきエラー（「インデントが揃っていません」）
- **実装方式**: INDENT / DEDENT トークンは字句側で出さず、パーサ側でトークンの行番号と行頭の空白から段を判定する。spell では深さ0でも演算子の後などで式が改行をまたいで続く（step 55）ため、論理行の終わりは字句側だけでは決められず、文の完了を知っているパーサに合わせて段を見るほうが既存の書き方を壊さないため。段は suite ごとの再帰で持つ
- **for の頭の `:` の曖昧性**: 反復対象への型注釈（`for i in x: [int] = [7, 8]`）は従来どおり使える。その位置では、式の直後の `:` は「型 = 」と続く場合だけ注釈として扱い、それ以外は suite の区切りとする。型の名前が実在することも条件にするため、suite の最初の文が `名前 = ...` という代入でも、その名前が型でなければ注釈と誤認しない
- prelude.sp は `{}` のまま書き換えない

## 決定: if / elif / while の条件の括弧は任意（step 69）

2026-11-27 に本人が決定。`:` 形式を正規形とする流れで、条件を囲む括弧も見た目をすっきりさせるため外せるようにする。

- **括弧は任意**: `if cond:` / `while cond { }` と書ける。従来の `if (cond) { }` もそのまま使える（prelude・既存コードは括弧形のまま）
- **対象**: `if` / `elif` / `while` の条件のみ。それ以外の括弧（関数呼び出し・ラムダ・型注釈など）は無変更
- **実装方式**: 条件は通常の完全な式として読み、終わりはブロックの開始（`{` か `:`）で判断する。括弧形は primary の括弧式としてそのまま読めるため、特別扱いは要らない。`if (a + b) * 2 > 3:` のように括弧式で始まる条件も、括弧を条件全体と誤認せず最後まで読む。直後の `:` が suite の区切りと競合する点は for の頭と同じで、型注釈の `:` は「型 = 」と続く場合だけ注釈として扱う（`cond_expr` が `suppress_anno` を立てる）
- **改行規則**: 条件も式文と同じ規則に従う（step 55）。演算子を行末に置けば次の行へ続けられ、括弧形では括弧の中は従来どおり改行自由

## 決定: 真理値リテラル `true` / `false` / `T` / `F`（step 70）

2026-11-27 に本人が決定。それまで spell に真理値リテラルはなく、`true` などは未束縛の識別子として読まれていた（bool 値は比較式などからしか作れなかった）。

- **4つの綴り**: 式の位置で `true` と `T` は真、`false` と `F` は偽のリテラルになる。`T` / `F` は短縮形。型は prelude の bool クラスで、実行時の値は従来の bool と同じ 1 / 0（比較結果ともそのまま混ぜられる）
- **実装方式**: トークナイザのキーワードにはせず、パーサの式（primary）の識別子解決でこの4綴りだけをリテラルノード（ND_BOOL）に変換する。typecheck は bool 型を返し、codegen は数値リテラルと同じ定数を出す
- **型の位置は無関係**: 型注釈・型パラメータ宣言・クラス名などの位置は primary を通らないため、`class Vec<T>` の `T` のような型パラメータ名は従来どおり名前として読める。メンバ名の位置（`obj.T`）も同様に対象外
- **帰結**: `true` / `false` / `T` / `F` という名前の変数は式の位置では作れない（代入先にすると「`true`には代入できません」のコンパイルエラーになる）。特別な救済は入れない
## 決定: 文頭 `<` の出力糖衣を削除する（step 71）

2026-11-27 に本人が決定。step 48 で `< "hello world"` を書けることを目標に導入した糖衣だが、比較演算子 `<` と見た目が紛らわしいため削除する。

- **文頭 `<` は削除**: 文の頭の `< 式;` は通常の構文エラーになる（特別なエラーメッセージは設けない）
- **`<<` は残す**: `<< 式;` は引き続き print の糖衣として使える
- **ドキュメントの例文**: リファレンスと糖衣集のコード例は、文終端のセミコロンを付けない正規形（`:` 形式・セミコロンなし）の見た目に揃える（同じ行に文を並べる箇所の区切りは除く）
